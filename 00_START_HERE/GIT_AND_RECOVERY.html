You can read and run the course from a fully extracted ZIP. Git is useful when you want a local history of your source edits. It is a separate workflow from saving the private evidence form or submitting a PDF.

To create a checkout, use an already available Git installation and Internet access. In a terminal, first open a parent folder where the new name below does not exist. Run each command separately and stop if it reports an error.

Bash on macOS/Linux

pwd
git --version
git clone https://github.com/antonioclim/WebTech_ASE.git WebTech_ASE_student
cd -- WebTech_ASE_student
git rev-parse HEAD

Windows PowerShell

Get-Location
git --version
git clone https://github.com/antonioclim/WebTech_ASE.git WebTech_ASE_student
if ($LASTEXITCODE -ne 0) { throw 'Clone failed. Preserve the existing folder and inspect the error.' }
Set-Location -LiteralPath WebTech_ASE_student
git rev-parse HEAD

If the destination already exists, choose a different new name or inspect the existing copy. Do not overwrite it. The public URL contains no credentials; do not add a password or token to it. An unavailable Git installation or connection does not prevent reading a previously extracted ZIP.

Identify the folder and inspect your changes

In VS Code choose File → Open Folder and select the actual extracted root or checkout. Open Terminal → New Terminal. A terminal that was already open can still point to another directory. Run the commands for your shell and compare the reported path with Explorer.

Bash

pwd
node -p "process.cwd()"
git rev-parse --show-toplevel
git status --short
git diff --stat
git diff --cached --stat

PowerShell

Get-Location
node -p "process.cwd()"
git rev-parse --show-toplevel
git status --short
git diff --stat
git diff --cached --stat

git rev-parse --show-toplevel reports the checkout root. If it says the directory is not a Git repository, check the path and whether this is an extracted ZIP. Do not initialise a repository merely to silence the message. Follow the seminar’s commands from its EN_GB root; a checkout’s overall root is not automatically the right working directory for every lesson command.

What the inspection commands mean
CommandQuestion answeredLimit
git status --shortWhich tracked files have staged or unstaged changes, and which non-ignored files are untracked?The two status columns describe index and working-tree changes; ?? means untracked. Empty output means no reported changes, not correct course work.
git diffWhat tracked edits are still unstaged?It does not show ordinary untracked file contents or changes already staged.
git diff --cachedWhat is staged for the next commit compared with the current commit?It can differ from the file you have since edited. Review both differences.
git rev-parse HEADWhat commit is checked out?That identifier does not include uncommitted edits or prove a test result.

Inspect one exact target with git diff -- 01_WEEKS/WEEK_01/S01_SEMINAR/EN_GB/CLASSROOM_RC6/targets/p01.mjs from the checkout root. If you are working on another project, substitute its exact editable path after checking the contract. The -- separates the path from command options. Private PDF and JSON backups belong outside this checkout.

Saving a file and committing it are separate actions

  1. If you want local history, begin from a known clean checkout and create a clearly named local branch before editing. For example, git switch -c student/s01-local creates and selects a new local branch if that name does not already exist. If you have already begun work, preserve a private backup first. Keep any unexplained changes and use a separate copy rather than discarding them.
  2. Edit your target and save it with Ctrl+S or Command+S. The runner reads the saved file on disk. An unsaved editor buffer is not tested by a terminal command.
  3. Run the seminar’s appropriate check from its stated working directory. Record the real result. Return to the checkout root and review git status --short, the target difference and any staged difference.
  4. Stage only the reviewed source target, for example git add -- 01_WEEKS/WEEK_01/S01_SEMINAR/EN_GB/CLASSROOM_RC6/targets/p01.mjs. This selects its current contents for the next commit. It does not run a check or upload anything.
  5. Read git diff --cached --stat and git diff --cached. Check that only your intended public source is present. Do not stage private evidence, credentials or protected support changes.
  6. Make a local commit whose message names the problem and behaviour, for example git commit -m "Record S01 classifier changes". Inspect git status --short afterwards. If Git cannot identify the author or a local hook refuses the operation, preserve your files and follow your institution’s setup guidance. Do not invent a successful commit.

A commit records the staged snapshot locally. It does not save later editor changes, publish a website, submit an assignment or make your work accepted. The course exercises do not require pushing to the shared course repository. Keep the ZIP or an untouched source copy alongside your working copy so that your changes remain distinguishable from supplied material.

Fetch first; integration changes your working copy

git fetch origin downloads remote objects and updates remote-tracking references. It does not automatically merge them into your working files. git pull fetches and then integrates according to its options and configuration, which can create a merge or rebase. A merge reconciles histories and may produce conflicts. These are different operations.

For an optional update in a known checkout, save all editor buffers and keep a private backup first. From the root, inspect the actual remote and current branch before fetching:

Bash

git status --short
git branch --show-current
git remote -v
git fetch origin
git log --oneline --left-right HEAD...origin/main

PowerShell

git status --short
git branch --show-current
git remote -v
git fetch origin
if ($LASTEXITCODE -ne 0) { throw 'Fetch failed. Preserve local work and inspect the error.' }
git log --oneline --left-right HEAD...origin/main

Stop if the remote is unexpected, the branch is unnamed, fetch fails or origin/main is absent. In this log, left markers identify commits unique to HEAD and right markers commits unique to origin/main. Review the actual changed paths before integrating. Do not paste a remote URL containing credentials into your evidence.

For a beginner with unfinished seminar edits, the simplest preserved-work update is a separate new download or clone. Keep the old folder and evidence, compare the source identities, then reapply only your own target changes to the new copy and repeat the relevant checks. Do not copy older contracts, runners or protected fixtures over the newer edition. An update may change the contract, so read it before transferring code.

If a merge was begun from a known clean copy and its work is backed up, git merge --abort attempts to restore the pre-merge state; verify the files afterwards. It is not a general undo command and may be unable to reconstruct pre-existing uncommitted changes.

Conflict markers such as <<<<<<<, ======= and >>>>>>> show alternatives, not executable code. Choosing “ours” or “theirs” without understanding the contract can discard valid work. Preserve the original, explain the resolution and re-run the witness that distinguishes the intended behaviour. If a recovery step cannot be completed, record BLOCKED with the actual reason rather than making the check appear green.

Official references for the command’s purpose

  • git-status: tracked, staged and untracked changes.
  • git-diff: compare the working tree, index and commits.
  • git-fetch: update objects and remote-tracking references.
  • git-pull: fetch followed by integration.
  • git-merge: integration, conflict resolution and the limits of abort.

References explain Git behaviour. They do not identify which edition you actually downloaded or certify your project. Record those facts from your own copy and observations.
