P01 — Normal reopen and explicit reset

Edit only: CLASSROOM_RC6/targets/p01.mjs. Interface: initialiseNotes(db, {reset=false} = {}).

Reason about the boundary

Starting the application should not silently delete a user’s data. The fixture creates the table and seeds it before your function runs. Normal initialisation preserves existing rows; an explicit reset deliberately restores exactly one seed.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
Normal initialisation followed by close/reopenOne Marker and one Seeded once remain
Explicit reset:trueMarker removed; exactly one Seeded once row remains

Implement in stages

  1. Read CLASSROOM_RC6/sqlite.mjs and the P01 lifecycle fixture as read-only references. Identify who creates the schema and seed. Do not duplicate that job on every normal call.
  2. Plan a normal path that preserves rows and an explicit reset path that changes the table. The reset seed is title Seeded once, owner Ada and archived 0.
  3. Run the lifecycle observation. Compare before, reopened and reset row arrays. Count markers and seeds rather than looking only at an initialisation return value.
  4. Explain the controlled temporary-file ownership and why orderly close/reopen is a narrower claim than recovering after power loss.
Progressive hints — open only when needed
  1. The default options object means reset is false when not supplied. Do not use a truthy fallback that turns the default into a reset.
  2. A schema initializer can be idempotent without deleting data. Here the schema is already supplied.

P02 — Closed query translator

Edit only: CLASSROOM_RC6/targets/p02.mjs. Interface: noteQuery(query).

Reason about the boundary

HTTP query values are text. The literal text "false" must become the archived binding 0 through an explicit accepted-token rule, not JavaScript truthiness. Data values belong in placeholders, while the order fragment must come from a fixed allow-list.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
{owner:" Ada ", archived:"false", sort:"title_asc"}where owner=? AND archived=?; bindings ["Ada",0]; order title ASC,id ASC
No filters, default sortEmpty where; empty bindings; order id ASC
archived:false, archived:"yes", unknown key or arbitrary SQL sortTypeError

Implement in stages

  1. List the only allowed own keys: owner, archived and sort. Distinguish an omitted option from an invalid present option.
  2. Trim and validate owner. Translate exactly true/false text tokens to numeric archived bindings. Do not concatenate owner data into SQL.
  3. Build the WHERE fragment and bindings in matching order. Choose sort from the two declared order strings; the default is id ASC.
  4. Observe the actual selected SQLite rows. Record the input, option object and row IDs/titles. Then test a disallowed sort before any database call.
Progressive hints — open only when needed
  1. The bindings order must match the order of placeholder fragments. A correct-looking SQL string with reversed bindings is still wrong.
  2. An order-by choice is structural SQL and should be selected from reviewed fixed strings rather than treated as a data parameter.

P03 — Awaited reservation persistence

Edit only: CLASSROOM_RC6/targets/p03.mjs. Interface: await saveReservation(store, input).

Reason about the boundary

Returning before a write settles would claim persistence prematurely. Validate the code before invoking store.create. Await the actual operation, then return detached saved data. Only the supplied ConflictError represents the mapped reservation conflict; unknown errors keep their identity.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
{code:" A7 "} with a successful store writeFresh {id:1, code:"A7"} for the supplied SQLite fixture
A second A7 in the unique storeError with code reservation_exists
Blank codeTypeError before create is called
Unexpected store errorThe same error object is propagated

Implement in stages

  1. Locate the supplied store interface and ConflictError class in the read-only experiment. Validate an own string code and nonblank trimmed value before any call.
  2. Plan the awaited create call with the trimmed code. Return a new object containing id and code from the saved row.
  3. Handle only the store’s declared conflict class. Preserve all other errors rather than turning every failure into reservation_exists.
  4. Run the real-write and delayed-completion witnesses. Record whether the returned promise stayed pending until the adapter released the row, plus the real unique-conflict observation.
Progressive hints — open only when needed
  1. The return value of an async function is a promise. A completed-looking placeholder object does not prove its underlying write finished.
  2. Error identity matters when the caller owns error handling. Do not replace an unrelated error just because it was thrown during creation.
