P01 — Concurrent request initiation

Edit only: CLASSROOM_RC6/targets/p01.mjs. Interface: await loadSummary(fetchImpl).

Reason about the boundary

Concurrency concerns when work begins. If you await the first fetch before starting the others, the requests form a waterfall. Start all three independent operations, then own their results. An HTTP error response is still a fulfilled fetch response and needs an ok/status check.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
Before releasing any deferred responsesAll three paths have been requested
Profile Ada, two open tasks, one notice{name:"Ada", openTasks:2, notices:1}
A non-ok response with status 404Reject with Error("http:404")

Implement in stages

  1. Read the three paths in the target comment. Predict the call list before any deferred promise is released, not only the eventual result.
  2. Separate the start phase from the await phase in your design. Every response must be checked before its JSON content is used.
  3. Derive the name, count of open tasks and notice count from the corresponding response bodies. Do not hard-code the fixture result.
  4. Run check and observe. Inspect the before-release call list and summary. Explain why a measured elapsed time alone would be weaker evidence of initiation order.
Progressive hints — open only when needed
  1. Promise.all can combine already-started operations. Constructing the inputs sequentially with awaits would defeat that purpose.
  2. The injected response provides an asynchronous json method. Receiving a response and reading its body are separate operations.

P02 — Delegated nested click

Edit only: CLASSROOM_RC6/targets/p02.mjs. Interface: delegatedAction(target, list).

Reason about the boundary

The clicked target may be a span inside a button. Delegation needs the nearest action button, then ownership by the list, then the nearest task row owned by the same list. The target’s own dataset is not an authoritative shortcut.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
Nested span inside owned delete button for T7{action:"delete", taskId:"T7"}
Matching button outside the owned listnull
No matching action button or unknown actionnull

Implement in stages

  1. Identify what the minimal injected nodes supply: closest(selector), contains(node) and dataset. Keep native browser claims separate.
  2. Plan nearest-button lookup with the exact selector button[data-action]. Refuse absence and list ownership failures.
  3. Resolve the nearest [data-task-id] row and confirm its ownership. Accept only toggle/delete. Return the exact action and task ID or null.
  4. Run the nested-target and outside-list witnesses. If you additionally execute a real browser click, record that separately with the actual browser and page.
Progressive hints — open only when needed
  1. The nearest matching button and the nearest owning task row are different elements.
  2. Finding an element is not evidence that it belongs to your component. Check containment.

P03 — Bounded retry classification

Edit only: CLASSROOM_RC6/targets/p03.mjs. Interface: isRetryable({kind, status}).

Reason about the boundary

This bounded policy uses explicit evidence labels. A transport rejection, an HTTP server status and invalid JSON are different events. Do not guess what an unknown label means. The function classifies; it does not perform retries or backoff.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
{kind:"transport"}true
{kind:"http", status:503}true
{kind:"http", status:404} or {kind:"parse"}false
Unknown kind or non-integer/out-of-range HTTP statusTypeError

Implement in stages

  1. Write a decision table for transport, parse and http before editing. Mark the unknown-label path as a definition error.
  2. For HTTP evidence require an integer status in 100–599. Apply the target’s >=500 policy only after validation.
  3. Keep retry classification separate from scheduling, retry counts and cleanup. Those full-application mechanisms are outside this exercise.
  4. Run the four observations and your own invalid case. Ask the approved LLM to critique one specific claim such as whether every parse failure should be retried, then execute an independent witness yourself.
Progressive hints — open only when needed
  1. A string status such as "503" must not silently become a numeric HTTP status.
  2. A policy result true does not mean a retry has happened or will succeed.
