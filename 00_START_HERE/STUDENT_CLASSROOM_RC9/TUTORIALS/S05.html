P01 — Closed task-body boundary

Edit only: CLASSROOM_RC6/targets/p01.mjs. Interface: taskBody(input).

Reason about the boundary

The service should receive a deliberately accepted representation. A closed body boundary rejects unexpected keys and wrong types rather than passing arbitrary request data onwards. Trimming the title should not mutate the caller’s object.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
{title:" plan ", completed:false}Fresh {title:"plan", completed:false}
completed:"false", blank title or additional admin keyTypeError
Properties supplied only through a prototypeTypeError

Implement in stages

  1. Write the only accepted own keys: title and completed. Decide how to refuse arrays, non-plain inputs and missing/unknown keys.
  2. Check the title is a string and becomes nonblank after trimming. Check completed is a boolean, not a truthy/falsy conversion.
  3. Construct a new two-field representation. Record the input before the call and compare it afterwards.
  4. Run checks and observe. Use a negative case that introduces a genuinely different unwanted key. Explain why refusing it before a service call matters.
Progressive hints — open only when needed
  1. Key allow-listing and type validation are complementary. One does not replace the other.
  2. A fresh returned object can contain a trimmed title while the original title remains unchanged.

P02 — Exactly-once terminal logger

Edit only: CLASSROOM_RC6/targets/p02.mjs. Interface: terminalLogger({id, start, clock, logger}) → terminal callback(status).

Reason about the boundary

Finish and close may both call the same terminal callback. The returned closure owns whether logging has already occurred. Its first accepted event supplies the status; later calls must not create another record or replace that status.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
start 100, clock returns 112; callbacks 201 then 499One record: {id:"R7", status:201, elapsed:12}
Two callback invocationsOne logger call, not two

Implement in stages

  1. Identify the outer creation stage and the returned callback stage. The outer function receives identity, start time, clock and logger.
  2. Plan one private closure flag whose lifetime lasts across callback invocations. Decide when that flag changes relative to emitting the record.
  3. Compute elapsed time from the supplied clock minus start. Avoid calling Date.now instead of the supplied clock, which would alter this contract.
  4. Run the finish/close witness and observe the exact logs array. Add a different callback sequence and compare count and first status.
Progressive hints — open only when needed
  1. A local variable recreated inside the callback cannot remember an earlier callback invocation.
  2. Exactly-once here means one emitted record for this supplied callback object. It is not a distributed exactly-once delivery guarantee.

P03 — Public outcome mapping

Edit only: CLASSROOM_RC6/targets/p03.mjs. Interface: publicOutcome(outcome).

Reason about the boundary

An internal outcome is not automatically safe to expose. The public layer deliberately chooses status, headers and body. A created resource needs a Location header; an unexpected internal failure needs a stable safe error envelope.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
{kind:"created", data:{id:7}}201; location /api/tasks/7; body {data:{id:7}}
not_found / conflict404 task_not_found / 409 task_exists
Unknown kind with private message500; {error:"internal_error"}, without the private message

Implement in stages

  1. Draw a table with columns for kind, status, headers and body. Include the default unexpected-error row.
  2. Implement one public envelope per outcome while keeping empty headers for non-created outcomes. Use the returned data ID for Location.
  3. Keep the private message out of the public response even when it is useful for internal diagnostics.
  4. Run P03 checks and actual HTTP observations. Record real status, location header and body from the loopback trace; distinguish these from calling the mapper directly.
Progressive hints — open only when needed
  1. A JSON body saying “created” does not make the HTTP response 201. Status and body are separate fields.
  2. Do not spread an arbitrary internal error object into a public envelope.
