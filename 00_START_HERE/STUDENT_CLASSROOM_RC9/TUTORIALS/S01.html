P01 — HTTP exchange classifier

Edit only: CLASSROOM_RC6/targets/p01.mjs. Interface: classifyExchanges(rows).

Reason about the boundary

A request path can contain a query without changing its pathname. A response Content-Type can contain parameters without changing the media type. Treat these as separate transformations. A method is not evidence of the body format: use the response media type in this bounded contract.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
GET /assets/detective.css; 200; text/cssGET, /assets/detective.css, 200, text/css, text
GET /api/clues?topic=css; 200; application/jsonGET, /api/clues, 200, application/json, json
POST /api/verdicts; 201; application/jsonPOST, /api/verdicts, 201, application/json, json

Implement in stages

  1. Open CLASSROOM_RC6/lesson-http.mjs as a read-only reference. Locate the three supplied exchanges. In the evidence form, write a three-row prediction before running your implementation.
  2. Open your P01 target. Keep the exported function name and the parameter. For each input row identify method, path, status, headers and body.
  3. Plan a new output record with exactly method, pathname, status, responseMediaType and bodyKind. Work on one boundary at a time: URL parsing, media-type parameter removal, then text/JSON classification. Preserve the input order and leave the source rows unchanged.
  4. Save, run the P01 check and then its observation command. Copy the actual printed origin and each request/response record. Compare these with your preserved predictions, including a prediction you got wrong.
Progressive hints — open only when needed

  2. Think about the difference between application/json; charset=utf-8 and application/json. Only the media type belongs in this output field.

P02 — Precise greeting resource

Edit only: CLASSROOM_RC6/targets/p02.mjs. Interface: greeting(method, pathname).

Reason about the boundary

Path recognition happens before decoding the name. A literal extra path segment must not accidentally become part of a valid resource. Once exactly one encoded segment matches, decode and trim it. Invalid encoding and an empty decoded name are input errors; a method other than GET on a matched route is a method error.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
GET /api/greetings/%20Ada%20Lovelace%20200; {message: "Hello, Ada Lovelace!", source: "path"}
GET /api/greetings/%20%20 or /api/greetings/%XX400; {error: "name_required"}
GET /api/greetings/Ada/extra404; {error: "not_found"}
POST /api/greetings/Ada405; {error: "method_not_allowed"}

Implement in stages

  1. Read the target comment. Draw a decision sequence for matched path, allowed method, decoding and nonblank trimmed name. The return value has status and body; do not start a listener inside this function.
  2. Implement path recognition first and run the named route-boundary check. Then handle the method decision. Keep the public error literals exactly as declared in the target.
  3. Add decoding with a controlled failure path. Trim the decoded name. Build a fresh success envelope rather than returning the raw encoded segment.
  4. Run P02 checks and observations. Inspect encoded-name, blank-name, extra-segment and method outcomes. In the HTTP observation distinguish the numeric status from the JSON body.
Progressive hints — open only when needed
  1. A percent-encoding failure can throw. Decide how to turn that particular input failure into the declared 400 envelope.
  2. Do not use a query parameter as the greeting name: this task takes its name from the path.
