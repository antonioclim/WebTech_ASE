P01 — Fresh task summary

Edit only: CLASSROOM_RC6/targets/p01.mjs. Interface: taskSummary(tasks, {owner="Ada", minimumEstimate=3} = {}).

Reason about the boundary

Filtering first can hide invalid data. Validate every task, including one that will not be selected. The selected output then owns its own array and projected records. Sorting a source array in place would alter the caller’s data.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
T1: Ada, done, estimate 9Valid but not selected
T2: Ada, open, estimate 5; T3: Ada, open, estimate 3Selected in T2 then T3 order; count 2; total 8
A task with estimate "9" as a stringTypeError, even when its status would filter it out

Implement in stages

  1. Read the task fixture in CLASSROOM_RC6/experiments.mjs without editing it. Predict the IDs, order, trimmed titles, count and total.
  2. Plan validation of the own string fields id/title/owner/status and finite numeric estimate on every record. Keep string and numeric values distinct.
  3. After validation, plan selection by owner, open status and minimum estimate. Construct fresh objects with only id/title/estimate and trim each selected title.
  4. Apply descending estimate order with ascending ASCII ID as the tie-breaker. Derive count and total from the selected result. Save, check and observe, including the input-preservation witness.
Progressive hints — open only when needed
  1. A new array can still contain old record objects. Decide where the projection creates a fresh object.
  2. Write the two sorting keys on paper before coding. A descending first key does not make the second key descending.

P02 — Declarative leaf rule

Edit only: CLASSROOM_RC6/targets/p02.mjs. Interface: compileLeaf(rule) → reusable predicate(record).

Reason about the boundary

The input is a description of one comparison, not executable JavaScript. Validate the description once, then return a predicate that checks a record’s own field. A numeric-looking string must not satisfy a numeric comparison through coercion.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
{field:"estimate", operator:"atLeast", value:3}, actual estimate 4true
The same rule, actual estimate "4"false
The same rule, estimate inherited from a prototypefalse
Unknown operator or atLeast value "3"TypeError while compiling the rule

Implement in stages

  1. Write down the two supported operators: equals and atLeast. Require the rule’s own field/operator/value properties and a string field name.
  2. Validate the definition before creating the predicate. For atLeast, the expected value must be a finite number. Reject an unknown operator explicitly.
  3. Inside the returned predicate, inspect ownership of the named record field. Apply exact comparison for equals; for atLeast require finite numeric actual data.
  4. Run the predicate more than once with different records. Observe numeric, string and inherited-field cases. Keep eval and new Function out of this bounded language.
Progressive hints — open only when needed
  1. Compiling a definition and testing a record are different stages. A bad definition should not produce a silently always-false predicate.
  2. Accessing a property can find a prototype value. Ownership needs a separate check.

P03 — Defensive event normaliser

Edit only: CLASSROOM_RC6/targets/p03.mjs. Interface: normaliseEvents(events).

Reason about the boundary

Normalisation projects an agreed representation; it does not make invalid input valid by guessing. The boolean false and the string "false" are different values. Equal timestamps require a deterministic ID tie-breaker.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
B and A both at time 1, with valid booleansOutput order A then B
active:"false"TypeError
A valid input record with an extra descriptive fieldOutput retains only id, time, active and duration

Implement in stages

  1. Plan validation for an array and each record’s own id/time/active/duration fields. Require a string ID, finite numeric time and duration and an actual boolean active.
  2. Build fresh output records with exactly the four declared fields. Do not repair a string boolean with truthiness or conversion.
  3. Sort the fresh output by ascending time and then ascending ASCII ID. Record a before snapshot of the input and compare it after execution.
  4. Observe both the array-fresh and record-fresh witnesses. Explain why a matching JSON output alone would not prove that the input was preserved.
Progressive hints — open only when needed
  1. The global function Boolean applied to a non-empty string does not parse the text “false”.
  2. Object identity and value equality answer different questions. Check both when the contract requires fresh records.
