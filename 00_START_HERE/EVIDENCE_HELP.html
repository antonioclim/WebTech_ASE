Record each project as you work

  1. Identify the source. Open the seminar’s supplied PACKAGE_ID.txt and copy its value into the form. Record the actual source copy and your environment. Describe edited targets as your working copy; the original package ID does not certify those edits. If you used a Git checkout, record its actual commit separately.
  2. Predict before running. State the input, the result you expect and the reason. Preserve that prediction. An expected output in a lesson is a comparison value until you run the corresponding action.
  3. Describe your own change. Name the exact editable path and the mechanism you changed. S01 uses CLASSROOM_RC6/targets/p01.mjs and p02.mjs; all three S02 projects use CLASSROOM_RC6/targets/styles.css. S03–S07 each use CLASSROOM_RC6/targets/p01.mjs, p02.mjs and p03.mjs in their own seminar. S08, S09, S10, S11, S12 and S13 each use CLASSROOM_RC6/student/p01.mjs, CLASSROOM_RC6/student/p02.mjs and CLASSROOM_RC6/student/p03.mjs in their own seminar. S14 uses only CLASSROOM_RC6/student/p01.mjs and CLASSROOM_RC6/student/p03.mjs. Keep the contract, test code, HTML fixture and supplied support unchanged.
  4. Record the actual action. Include the terminal’s working directory, exact command, input and observed exit code. In a browser, give the exact page, action, browser version and relevant viewport or preference. A command copied from instructions is not a record of execution.
  5. Copy the relevant result. Include the output or behaviour you actually observed. Retain failures and label anything unexecuted. Explain a mismatch rather than replacing it with the expected value.
  6. Try a case that could contradict your rule. Design your own boundary or falsifying case. State its prediction, action and actual result. If setup stopped before the claimed mechanism ran, record the blocker rather than a successful falsifier.
  7. Make the evidence findable. Name the project heading and relevant output in the same record, or a precise labelled page in the final PDF. A path to an image does not embed it.
  8. Explain the result and its limit. Connect the mechanism to the observation, say what changed in your understanding and name any conclusion that needs another kind of evidence.

Critique one AI claim for the whole seminar

  1. Choose one narrow explanation or hypothesis from your own work. Identify its assumption and a result that could contradict it. An HTTP claim needs an HTTP witness if that is the behaviour claimed; a rendered CSS claim needs the actual browser conditions.
  2. Prepare a small synthetic input or sanitised public excerpt. Your required identity belongs only in the private PDF and backup. Never send names, group details, marks, student records, credentials, tokens, real cookies or private code to the AI service.
  3. Use Gemini or the institution’s approved LLM for a real exchange. Ask for a critique of the claim, its assumptions or a counterexample. Do not request the complete assessed implementation. Record the actual tool, date, sent prompt and relevant response; do not replace them with a sample dialogue.
  4. Select one concrete claim from the response. Run an independent action that could distinguish the claim from a plausible error. Copy your actual input, command or browser action and result.
  5. Give your supported verdict and correction, with the remaining limit. A justified UNKNOWN after an inconclusive check can be truthful. Reading the model’s answer without performing the check leaves that check unfinished.

If AI access is unavailable: select BLOCKED and record the attempted step, observed message or unavailable prerequisite and next safe action in Blockers. Do not invent a response. Continue independent project work where possible. Your lecturer determines the authorised way to finish the missing AI activity; this guide does not waive it.

Save a private draft and recover it safely

  1. Use the form’s JSON backup button during work. Choose a private folder outside the protected kit and public Git repository. The form requests a download; check that the actual file exists and opens as JSON. The unsaved indicator records edits in this page, not a receipt from your filesystem.
  2. These forms do not use localStorage or automatic browser storage. Reloading, closing or resetting can lose unsaved text. Browser history and a PDF are not editable JSON backups.
  3. Before importing, export your current record and verify that backup. An accepted import replaces the current text and statuses and resets every declaration. It does not merge two drafts. Select the matching seminar and setup form; a wrong schema, unexpected field or over-sized file is refused before replacement.
  4. After import, check the package identity, source, statuses and evidence yourself. Renew only declarations that you can support. A later material edit clears declarations again.
  5. If a field or backup exceeds the stated limit, remove irrelevant quotations while preserving the witness. Keep a longer private log separately and copy the necessary supported result into the PDF.

If a backup fails to import, keep the original file. Confirm the form and setup identifier, read the visible refusal and recover text from a private copy. Do not edit metadata to make one seminar’s backup impersonate another. See working-copy recovery for source problems.

Review one PDF for the whole seminar

  1. Review every required project and the single genuine AI critique. Explain blockers and retain failed attempts. Form controls can check presence and format, while the quality and truth of your work still require human review.
  2. Use the form’s reviewed-evidence or completed-record print action only after the required evidence and manual declarations are ready for review. S03–S14 label this as a reviewed student declaration with human review pending. Otherwise use the clearly labelled draft or blocked print action. Printing an unfinished record preserves evidence; it does not complete missing work.
  3. Copy the form’s suggested filename. The copy button uses the browser clipboard when available, or selects the name so that you can press Ctrl+C or Command+C. In the native print dialogue choose Save as PDF and enter that name.
  4. The form prints text. If screenshots are required, capture the actual claimed behaviour, add a labelled page with an approved local document/PDF tool and merge it into this same seminar PDF. A screenshot path alone does not include its contents.
  5. Reopen the actual saved PDF. Inspect every page, the identity, scope banner, all required project headings, genuine AI exchange, output lines and any images. Check that nothing is clipped, missing or too small to read.
  6. Follow the actual Moodle Assignment instructions to submit that one file. A local export, filename or form status does not confirm upload, final submission or acceptance. Only a real observed Moodle result can support a submission claim.
