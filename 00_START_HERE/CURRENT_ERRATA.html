# Lecture Example — Service Worker Scope Decision

## Concept demonstrated

Registration, readiness and current client control are different states. This example observes controller state and asks an available registered worker to classify a small set of request descriptions.

## Why this example is in the lecture

The page performs registration and waits for readiness. It selects the current controller when one exists, otherwise the registration's active worker, then sends typed request descriptions through `MessageChannel`.

## What to observe

- Read the displayed `controlled` value separately from the returned classifications.
- The worker returns `message` for a same-origin `GET /api/tasks/:id` and `network` for writes or unrelated paths in the supplied cases.
- An uncontrolled page can still obtain a `message` classification through the active-worker fallback. This example does not enforce a controller-before-message policy.

## Run / inspect

```bash
node server.mjs
# Open http://127.0.0.1:4214
```

## Explanation

The worker classifies the supplied method, absolute URL, origin and pathname. The `message` and `network` values are decision labels. The supplied worker has no fetch or cache handler, so the labels do not establish actual network forwarding, a cache hit or an uncontrolled-request network fallback.

## Variations

- Add an explicit controller requirement and specify what an uncontrolled page should do before comparing that changed implementation with this example.
- Add a separate navigation policy and explain which fetch or cache behaviour would require implementation and observation.
- Decide whether controller replacement should retry or reject pending work.

## Validation

Preserved historical headless observations remain evidence for their recorded registration and message behaviour on the tested source. They do not establish a controller-before-message rule, actual network forwarding or cache behaviour. This documentary correction changes no executable code or historical receipt.
