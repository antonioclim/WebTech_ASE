C14 — Build a claim from observations

A useful test or measurement has a declared input, a controlled boundary, an observable result and a limit. Work through those four facts before calling evidence sufficient.

1. Choose a boundary that can observe the claim

Input and owner. The canonical task system separates title policy, an in-memory repository and an Express route. Each test observes a different contract. A test runner's green result describes the assertions it executed, not every component that happened to be imported. Node's test runner supports isolated tests and cleanup hooks, but the test author still owns sufficient assertions and resource cleanup. [Node test runner]

Source: 01-test-boundary-selector/system.mjs and its unit, integration and API tests.

Three worked claims about the same task
Input / operationState and observationSufficient local conclusionLimit
Call title policy with " Read "Trims to "Read"The stated normalisation case passes at a unit boundaryNo HTTP, repository or empty-input result follows from this one assertion
Insert {title: "Read"}, then retrieve all rowsRow gets ID "1"; retrieved row is a detached copy. Mutating a retrieved copy does not alter the next readThis in-memory repository preserves that read boundaryNo database transaction, durable storage or process-restart evidence
POST /tasks with the titleLoopback response is checked for 201, Location: /tasks/1 and the JSON representationThe observed create response satisfies these HTTP assertionsThe API test does not read state afterwards; it does not alone prove persistence
  1. Write the claim precisely. “The create response has status 201” needs a response; “created state can be read later” needs a state follow-up.
  2. Select collaborators. Use a pure function for local policy, a real repository for repository behaviour and HTTP for the public route contract. Browser-owned focus, navigation, storage or Worker behaviour needs browser evidence.
  3. Own the lifecycle. Establish fixtures and readiness before the action. Ensure cleanup is registered even when an assertion fails; await asynchronous closure when later tests depend on it.
  4. Record the observation. Include the assertion and result, rather than only the command's exit code.

Limit. “Integration” here joins an application-owned in-memory repository; it does not secretly mean a production database. Higher boundaries may be necessary for a different claim, but importing more components does not strengthen an assertion about behaviour it never observes.

2. Show which defect an assertion detects

Input and owner. The canonical example chooses one of three service variants, sends a create request, reads the list and triggers a deliberately synthetic failure. Its inspector returns three booleans: creation status, persistence and sanitisation. The test compares the complete vector with the expected vector for each variant.

Source: 02-seeded-defect-sensitivity/service.mjs and service.test.mjs.

  1. Predict before running. The wrong-status variant should change only the status observation. A missing-persistence variant should change the follow-up list. A leaked-error variant should change the public failure text.
  2. Stimulate through the public boundary. Create a task with POST /tasks, then use GET /tasks to inspect stored state. Separately send the fixture's explicit failure input.
  3. Observe three facts. Compare creation status with 201; compare stored count with 1; check that the synthetic marker is absent from the failure response.
  4. Compare vectors. A variant is detected only when the observed difference matches the intended defect. A crash or unrelated setup error is a different result.
The source's expected observation vectors
Service variantStatusPersistenceSanitisationReason for the failed observation
wrong-statusFalseTrueTrueReturns 200 for creation
missing-persistenceTrueFalseTrueReturns a task without storing it
leaked-errorTrueTrueFalsePlaces the fixture's synthetic secret marker in public error text

Interpreting a green suite. This lecture test passes when it successfully recognises these deliberately faulty variants. Its overall pass does not certify a production service. More generally, a passing baseline establishes the environment for a task; an objective assertion distinguishes required behaviour; a regression assertion protects another named contract. Coverage reports executed code, while a targeted fault probe asks whether an assertion notices a behavioural difference.

Limit. The canonical inspector closes its server only on the normal path and does not await closure in a guaranteed finally. An earlier rejection can bypass cleanup. Its sanitisation test searches for one fixture marker; it does not prove every sensitive value is excluded. A “killed” flag copied into a report is not evidence that a defect was applied and an assertion executed.

Evidence record. Preserve the control identity, changed fault, exact failing assertion, result class and cleanup outcome. If a fault survives, distinguish an equivalent change, an unreachable scenario and a missing assertion before changing the claim.

3. Define and calculate a tail metric

Input and interval. The canonical endpoint delays nine requests by 10 ms and one by 200 ms. Its probe issues ten requests sequentially, starts a timer before fetch and stops after the Response becomes available. It does not consume the body before stopping. Response availability and body completion are separate points in Fetch, so the README's body-completion description is broader than this source. [Fetch standard]

Source: 03-tail-latency-trace/probe.mjs and probe.test.mjs. The numbers below are a fixed arithmetic example, not measured durations or assumed runtime overhead.

Sorted sample in milliseconds: 10, 10, 10, 10, 10, 10, 10, 10, 10, 200
Count n = 10; sum = 290
Mean = 290 / 10 = 29 ms
Nearest-rank p95 index (one-based) = ceil(0.95 × 10) = 10
p95 = tenth observation = 200 ms; maximum = 200 ms

State and result. Sorting gives the order statistics; the mean summarises all values, whereas this nearest-rank rule selects a position. With only ten observations, p95 selects the maximum. It reveals the fixed sample's tail but cannot estimate a service-level objective with useful confidence by itself. A percentile claim must state its algorithm, population and aggregation method. Histogram and summary aggregation have different semantics. [Prometheus histograms and summaries]

Concurrency, throughput and failures are different quantities

A fixed scenario that completes 60 operations in 10 measured seconds has an observed completion rate of 6 operations per second. That arithmetic says nothing about its maximum in-flight work. A scheduling cap of 2 describes concurrency, not that rate. Both statements need their own observations and the same declared interval.

An HTTP 503 response is an HTTP outcome that a Fetch caller must inspect; a rejected request is a transport-level outcome; a locally imposed deadline is a client policy outcome. A local abort does not by itself prove the server stopped doing work. Keep failed and expired work visible when reporting the distribution. [Fetch standard]

Limit. The canonical probe has no explicit deadline, HTTP status classification or body-consumption timing. Its tail assertions demonstrate a bounded teaching sample on the tested environment; they do not establish capacity, production load tolerance or an SLO. The server's requested delay values are not the measured network durations.

4. Project a request into a log event

Input and owner. The canonical test sends a deliberately secret-bearing synthetic login request. The middleware owns the completion-event schema. On response finish, it creates a new object containing selected fields rather than serialising the request. The route responds with a public 401 and a generic error representation.

Source: 04-safe-log-projection/server.mjs and server.test.mjs.

  1. Start. Capture the local start time and register a response-finish listener.
  2. Handle. The request passes through the route; its body and authorisation header are not copied into the event.
  3. Project. Emit timestamp, level, event name, request ID, method, path, status and rounded duration.
  4. Observe. The test checks the exact event keys, the supplied request ID and absence of its synthetic secret marker.
  5. Interpret. The event witnesses this middleware projection. It does not show client rendering, successful authentication or all possible downstream log emissions.

Operational use. Logs describe events; metrics aggregate observations; traces correlate work across boundaries. Stable event schemas, data minimisation, access control, retention and sanitisation of untrusted fields require explicit ownership. [OWASP logging guidance] For metrics, a route template such as /tasks/:id offers a bounded label set; an arbitrary task ID, email or request ID does not. Every distinct label combination can create another time series. [Prometheus instrumentation]

Limit. The test's 5 ms delay is an arbitrary wait for a side effect. An event or promise is a stronger readiness witness. The allowlist reduces leakage but does not validate the copied request ID or raw path, enforce retention, or prove that the full log pipeline is safe. The derived helper's internal ID and route-template fields are a separate explanatory design.

5. Preserve pass, fail and unknown before applying policy

Input and owner. The canonical reviewer runs a syntax command, tries to run an intentionally missing audit tool and records whether a TLS report was supplied. Each observation has a state and a required flag. The policy blocks when any required row is not a pass.

Source: 05-evidence-tristate-gate/review.mjs and review.test.mjs.

Expected observations in the canonical pre-deployment example
Evidence attemptStateRequired?Policy effect
Syntax command exits 0PassYesThis row permits progress
Audit executable cannot be startedUnknownYesBlocks; no audit observation exists
No deployment-owned TLS report suppliedUnknownNo at this stageVisible outstanding evidence; not this gate's blocker
  1. Collect. Record an actual command outcome or an identifiable external artefact. A claim string alone is not an observation.
  2. Classify. A completed check may pass or fail. A missing tool, absent report or failed evidence collection leaves a stated unknown. A non-zero exit needs interpretation: it can indicate a detected problem or a failed check.
  3. Apply stage policy. Mark which claims are required for this review stage. Required unknowns block; non-required unknowns remain in the record.
  4. Assign action. Every fail or unknown needs an owner, next step and limit. An exception also needs its scope, reason and expiry.
  5. Re-evaluate with new evidence. At a deployment gate, the TLS requirement may become mandatory. A pre-deployment decision does not carry over unchanged.

Limit. In the canonical source any truthy tlsReport becomes a pass, without schema, authenticity, target or time checks. Its subprocess runner also has no bounded timeout. The tri-state representation preserves uncertainty in the illustrated cases; it does not authenticate evidence. The derived typed-evidence helper checks fields, but field validity still does not prove the claimed command or deployment observation happened.

Useful record. Include claim, target identity, environment, command or artefact source, observation time, state, required stage, owner, next action and what was not tested. Keeping those fields allows a reviewer to distinguish “a check passed here” from “this target is ready for this stage”.

6. Make production readiness a bounded argument

Locked installation, build, application start, health, shutdown and deployed operation answer different questions. npm ci expects a lockfile consistent with the manifest and does not repair mismatches. An audit asks the configured registry about known vulnerabilities in its dependency scope; it is not a proof that every vulnerability is absent. Record the invocation, scope and collection outcome. [npm ci] [npm audit]

Graceful shutdown should stop accepting new work, allow named in-flight work to complete according to policy and release resources. Health checks help deployment infrastructure decide which instances can receive traffic. Their meaning and deadlines must be defined for the application. [Express health and shutdown]

Keep a change's impact connected to evidence

Suppose a task update now emits a notification after persistence. The impact map includes route inputs, trusted identity, repository commit, event publication, public response, retry and cleanup. If persistence fails, publication should follow the chosen failure policy rather than imply a committed update. If publication fails after a commit, record whether the application retries, keeps pending delivery state or uses an outbox. This is a design scenario; no one policy is implemented by the lecture examples.

A maintainable change preserves named contracts and puts ownership where failures occur. An AI suggestion still needs the same impact map, allowed-file boundary and independent evidence; a generated explanation is not an execution receipt.
