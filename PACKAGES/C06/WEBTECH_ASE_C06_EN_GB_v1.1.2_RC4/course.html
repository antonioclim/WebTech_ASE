C06 · 01 / 24 · 00–03 min

What survived, and across which boundary?

Last week, a task could be created and retrieved while one process was alive. This week, that observation is not enough to establish file persistence.

create row → await write → close connection
reopen the SAME storage → find the SAME row

Which part of this sequence has your evidence actually crossed?

A create/read in one connection proves less than close/reopen of the same file. A process restart is a further boundary. None alone is a crash or power-loss durability test.

Not null is not the same as not empty

Nullability, nonblank content, uniqueness and defaults constrain different cases. Do not treat a validator declaration as proof of every SQL constraint.

title: { allowNull: false, validate: { notEmpty: true } }

What would distinguish a JavaScript validation from a SQL constraint?

Use the real model validation, inspect the created schema and test the relevant write boundary separately. allowNull has both Sequelize and SQL effects after synchronisation; notEmpty is not by itself a SQL CHECK.

C06 · 07 / 24 · 16–19 min

Initialisation and reset are different policies

Ordinary startup, schema migration, fixture seeding and destructive reset are different operations. A convenient testing shortcut is not a durable startup policy.

await sequelize.sync(reset ? { force: true } : undefined);
if (await Note.count() === 0) {
  await Note.create({ title: "Seeded once" });
}

Which explicit choice permits old rows to disappear?

reset:true requests force synchronisation. In the source example that is deliberate and isolated in a new temporary directory. It is not a migration strategy and must never be pointed at a user database.
