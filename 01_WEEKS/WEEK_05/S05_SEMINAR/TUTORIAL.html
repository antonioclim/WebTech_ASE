P02 — Exactly-once terminal logger

Edit only: CLASSROOM_RC6/targets/p02.mjs. Interface: terminalLogger({id, start, clock, logger}) → terminal callback(status).

Reason about the boundary

Finish and close may both call the same terminal callback. The returned closure owns whether logging has already occurred. Its first accepted event supplies the status; later calls must not create another record or replace that status.

Contract examples to predict before execution; these are not your observations

start 100, clock returns 112; callbacks 201 then 499One record: {id:"R7", status:201, elapsed:12}
Two callback invocationsOne logger call, not two

Four semantic stages and their witnesses

1. Create one callback with private memory

Input and action. In targets/p02.mjs, distinguish creation of terminalLogger from invocation of its returned callback. The creator receives id, start, clock and logger. Predict that one callback invoked with 201 then 499 can remember its first event, while a separately created callback has its own first event.

Why this changes the result. A variable recreated inside every callback starts over. A global variable would instead share decisions between requests. The required lifetime belongs to the particular returned function. This is C03’s closure mechanism and C04’s ownership question applied to a terminal decision.

P03 — Public outcome mapping

Edit only: CLASSROOM_RC6/targets/p03.mjs. Interface: publicOutcome(outcome).

Reason about the boundary

An internal outcome is not automatically safe to expose. The public layer deliberately chooses status, headers and body. A created resource needs a Location header; an unexpected internal failure needs a stable safe error envelope.

Input or conditionExpected contract behaviour
{kind:"created", data:{id:7}}201; location /api/tasks/7; body {data:{id:7}}

Four semantic stages and their witnesses

1. Describe the complete public decision table
