Exercise Specification — API Contract Repair

Unit

Unit 05 — Server-Side JavaScript and REST APIs

Learning objective

Repair an Express API boundary so service outcomes and thrown failures produce consistent status codes, headers, success envelopes and centralised JSON errors without rewriting working domain logic.

Why this exercise exists

Generated APIs often contain individually plausible routes that return 200 for every result, expose inconsistent shapes or catch errors locally. This project asks students to infer one public contract from tests/runtime evidence and make a bounded boundary-layer repair.

Prerequisites

  • In-memory Task API and Middleware Pipeline.
  • HTTP status/error semantics and Express middleware order.
  • Experience reviewing a one-module repair from Unit 1.

Starting context

Students receive an Express 5 ESM service for meeting invitations. Supplied route handlers parse inputs and call an intentionally preserved legacy-meeting-service.js. The service returns one of these frozen outcome objects or throws:

  • { kind: 'listed', meetings };
  • { kind: 'created', meeting };
  • { kind: 'accepted', meeting };
  • { kind: 'missing', resource: 'meeting' };
  • { kind: 'conflict', code: 'already_accepted' };
  • { kind: 'invalid', code, message };
  • an unexpected thrown Error.

Routes delegate every result to sendServiceOutcome(response, outcome) and forward thrown failures to apiErrorHandler(error, request, response, next). Both exports live in the incomplete src/http-contract.js. A supplied src/legacy-http-fallback.js contains the deliberately naïve raw-200 outcome sender and error-message responder used only when the repair boundary is absent; it is preserved unchanged in both versions and is explicitly not production practice. App assembly, routes, service, static landing page, fixtures and tests are supplied and must remain unchanged.

Required behaviour

  • Listed meetings return 200 and { "data": meetings }.
  • Created meetings return 201, Location: /api/meetings/<id> and { "data": meeting }.
  • Accepted invitations return 200 and { "data": meeting }.
  • Missing meetings return 404 and { "error": { "code": "meeting_not_found", "message": "Meeting not found" } }.
  • Already-accepted invitations return 409 and { "error": { "code": "already_accepted", "message": "Invitation already accepted" } }.
  • Invalid service outcomes return 400 and preserve only their documented public code and message in the standard error envelope.
  • Every JSON response declares application/json; no recognized operation returns a bare object/array or success status for an error.
  • sendServiceOutcome returns after sending, does not mutate a frozen outcome and throws TypeError('unknown service outcome') for an unrecognized kind so centralised handling owns the failure.
  • apiErrorHandler maps malformed Express JSON errors to 400 invalid_json.
  • Other thrown errors produce 500 and { "error": { "code": "internal_error", "message": "Internal server error" } } without exposing message, stack or arbitrary properties.
  • If headers have already been sent, the error handler delegates to next(error) instead of attempting a second response.

Constraints

  • Use JavaScript ESM, Express 5, Node.js LTS, native fetch and Node's test runner.
  • Repair only src/http-contract.js; do not edit legacy service logic, routes, app assembly, fixtures or tests.
  • Add no dependencies and do not introduce route-specific catches.
  • Use the course-wide { data } success and { error: { code, message } } error shapes.
  • Do not serialize unexpected error details.

Observable completion criteria

  • Initial objective checks show wrong statuses/envelopes while health/static/baseline behaviour remains green.
  • After repair, list/create/accept/missing/conflict/invalid outcomes match the exact public contract.
  • Malformed JSON and an injected thrown failure reach consistent centralised errors.
  • The final diff touches only src/http-contract.js and all automated checks pass.
  • The student can explain why each service outcome maps to its HTTP status and why unexpected errors are handled centrally.

Validation plan

Baseline checks

  • Server startup, health/static routes, route-to-service calls and all preserved legacy outcomes work independently of the repair module.
  • The legacy service and outcomes remain unchanged/frozen.

Objective checks

  • Every recognized outcome maps to the specified status, optional Location, envelope and JSON media type.
  • Frozen outcomes are not mutated.
  • Unknown outcomes throw into centralised handling.
  • Malformed JSON, unexpected errors and headers-sent delegation match the error-middleware contract.

Regression checks

  • Invalid request parsing still prevents a service mutation.
  • Unknown routes remain 404 not_found through supplied fallback middleware.
  • A failed request does not prevent a subsequent list/health request.
  • No internal error data appears in serialized responses or captured output.
