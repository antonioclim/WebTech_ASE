S03 — Validate data, preserve ownership and construct a small rule

Teaching revision for the v4.0.0 candidate; the retained implementation folder is still named CLASSROOM_RC6. Complete all 3 projects individually. The full required route is planned for 120–165 minutes and remains unpiloted. Complete Day 0 extraction, editor setup and capability checks before class. These instructions do not award a grade or invent a deadline.

We will turn three explicit data contracts into small JavaScript transformations. Validate before selecting, create the records the result owns and preserve the caller’s data. Separate a correct value from a correct ownership boundary.

What you will learn

  • Validate every input record before selecting a subset.
  • Build fresh records and deterministic ordering without mutating inputs.
  • Distinguish own fields and exact types from inherited or coerced values.

These tasks execute actual JavaScript modules over fixed synthetic fixtures. The rule task implements one leaf, not a recursive rule language. There is no browser or HTTP requirement in this core route.

P01 — Fresh task summary

Edit only: CLASSROOM_RC6/targets/p01.mjs. Interface: taskSummary(tasks, {owner="Ada", minimumEstimate=3} = {}).

Reason about the boundary

Filtering first can hide invalid data. Validate every task, including one that will not be selected. The selected output then owns its own array and projected records. Sorting a source array in place would alter the caller’s data.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
T1: Ada, done, estimate 9Valid but not selected
T2: Ada, open, estimate 5; T3: Ada, open, estimate 3Selected in T2 then T3 order; count 2; total 8
A task with estimate "9" as a stringTypeError, even when its status would filter it out

Invariant: validate every record before selection, return fresh id/title/estimate views and leave the caller’s data unchanged. Course link: Value/Shape/Effect, with Identity witnesses.

Four stages and their local witnesses

1. Validate the whole input

Input and action. Begin with the read-only fixture in CLASSROOM_RC6/experiments.mjs: input order is T1, T3, T2. In targets/p01.mjs, establish the array/record boundary and require own string id/title/owner/status fields plus a finite numeric estimate on every record. Predict TypeError for the supplied excluded done task if its estimate is changed to the string "9".

Why this changes the result. Validation decides whether the caller supplied admitted data; selection later decides which valid records matter. Filtering out the done task first would hide malformed input. This is C03’s Value lens and boundary-before-pipeline rule. Do not add positivity, non-empty IDs or other restrictions absent from the task contract.

Observe and check. Run node CLASSROOM_RC6/kit.mjs check P01, then node CLASSROOM_RC6/PROBE.mjs P01-boundary from S03 EN_GB. Inspect P01.validate-filtered-record and the actual probe’s error name. The whole P01 check also includes summary and freshness; those may still fail while later stages remain TODO. A syntax error or crash is not a recognised partial-stage result.

Trap, recovery and continuation. If an excluded string estimate produces a normal summary, first inspect whether selection precedes the full validation pass. Move only the validation obligation to the input boundary and repeat that excluded record plus a valid numeric record. Continue when the invalid excluded record is refused with TypeError, while preserving the remaining TODO list.

2. Select and project fresh records

Input and action. With admitted data, select the requested owner, open status and minimum estimate. The default configuration is owner Ada and minimumEstimate 3. Predict T1 valid but excluded, with T3 and T2 selected before ordering. Construct new output records containing only id/title/estimate; trim the selected titles in the new representation.

Why this changes the result. T1 fails a selection rule rather than a type rule. filter creates a container while retaining selected records; the projection must create the result records separately. This uses C03’s Shape and Identity lenses. Reading a title and returning its trimmed value is different from assigning that value to the source title.

Observe and check. Run node CLASSROOM_RC6/kit.mjs check P01 and node CLASSROOM_RC6/kit.mjs observe P01. Compare the source rows and current projected fields. P01.fresh-and-unchanged inspects input content, array identity and record identities. Freshness comparisons on an empty result would be vacuously true in isolation. The current P01.fresh-and-unchanged case also requires the expected two result records; the TODO empty array therefore fails this case as well as P01.selected-summary. Ordering/count/total may still be unfinished.

Trap, recovery and continuation. If source titles lose their spaces, inspect assignments to source records; remove the source write and repeat the before/after check. If output records are shared, locate the projection step that still returns the source object. Continue when T2/T3 have fresh projected records and the caller’s titles retain their original text.

3. Order and summarise the selected population

Input and action. Sort the result you own by estimate descending, then ASCII ID ascending on equal estimates. Derive count and total from this selected result. Predict T2/beta/5 before T3/gamma/3, count 2 and total 8. In an external private experiment begin with equal-estimate IDs a then B; predict B then a.

Why this changes the result. The two keys have different directions. A numeric total is meaningful only when its population is the selected one. C03’s course claims example totals 11 and canonical example 04 totals 6 because they have different fixtures; neither number replaces S03’s 8. Sorting mutates its receiver, so identify which array is being sorted.

Observe and check. Run node CLASSROOM_RC6/kit.mjs check P01 and node CLASSROOM_RC6/kit.mjs observe P01. Inspect P01.selected-summary against the full object rather than reading only total. Execute the equal-estimate variation with your own private probe; the original observer fixture has unequal estimates and cannot alone discriminate the tie rule. The strengthened P01.fresh-and-unchanged checker also uses equal-estimate IDs a/Z and expects Z/a, so its result now discriminates ASCII order. Your own meaningful case remains required.

Trap, recovery and continuation. If total includes T1, trace which population supplies reduce rather than changing the final arithmetic. If a tie retains a/B, inspect the second key and avoid locale-dependent collation for this ASCII contract. Correct the selected population or comparator, rerun the same discriminant and reconfirm source preservation. Continue when both primary order and the explicit tie agree with the contract.

4. Compare value, source and identity

Input and action. Use the saved implementation and preserved prediction. Run node CLASSROOM_RC6/kit.mjs check P01, node CLASSROOM_RC6/kit.mjs observe P01 and your meaningful additional case. Final P01 is expected to report PASS_BOUNDED_CLASSROOM_CHECKS with all three named assertions passing; retain your actual report.

Why this changes the result. Value equality, unchanged source content and fresh identities require separate witnesses. Observe P01 prints copied input and output, not explicit arrayFresh or recordsFresh fields. The named freshness assertion supplies identity checks; an additional private before/after and reference comparison can make those observations explicit. A plausible total cannot establish them.

Observe and check. Challenge the validation-before-selection rule with your own invalid record that would be excluded, or challenge the second ordering key with a/B at equal estimates. P02 — Declarative leaf rule

Edit only: CLASSROOM_RC6/targets/p02.mjs. Interface: compileLeaf(rule) → reusable predicate(record).

Reason about the boundary

The input is a description of one comparison, not executable JavaScript. Validate the description once, then return a predicate that checks a record’s own field. A numeric-looking string must not satisfy a numeric comparison through coercion.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
{field:"estimate", operator:"atLeast", value:3}, actual estimate 4true
The same rule, actual estimate "4"false
The same rule, estimate inherited from a prototypefalse
Unknown operator or atLeast value "3"TypeError while compiling the rule

Invariant: separate a valid own-field leaf definition from the record later evaluated, without coercion or dynamic evaluation. Course link: Property/Function, with exact Value checks.

Four stages and their local witnesses

1. Describe the admitted leaf

Input and action. In targets/p02.mjs, read the rule as data describing one comparison. Require its own field/operator/value properties and a string field name. Only equals and atLeast belong to this language. For atLeast, the expected value must be a finite number. Predict TypeError when the operator is unknown or its numeric threshold is a string.

Why this changes the result. A definition is the authority for the later comparison, so invalid configuration must be refused at compilation. Do not forbid extra fields or invent a recursive syntax: the public contract admits one leaf and states only the required own fields. This uses C03’s Property lens before its Function lens.

Observe and check. Run node CLASSROOM_RC6/kit.mjs check P02. Inspect P02.invalid-definition separately from P02.strict-leaf; the predicate behaviour can still be TODO. In your own external probe, catch the particular TypeError and record whether it happened when calling compileLeaf, not while evaluating a later record.

Trap, recovery and continuation. If an unknown operator quietly yields an always-false predicate, inspect the compile-time refusal branch. Restore the declared TypeError, repeat the unknown operator and a valid definition and retain any remaining predicate TODO. Continue when bad definitions are refused before a predicate is returned.

2. Capture validated configuration

Input and action. After accepting the definition, create one reusable predicate and retain the selected field, operator and expected value through its closure. Predict that the same predicate can evaluate several records using the same validated definition. Creation and each later call are distinct events.

Why this changes the result. C03’s factory example demonstrates a function retaining lexical configuration rather than getting a threshold from this. A closure keeps access to bindings; it is not automatically a deep frozen snapshot of arbitrary objects. The task needs a validated leaf configuration, not dynamic JavaScript execution. Keep eval and new Function out.

Observe and check. Run node CLASSROOM_RC6/kit.mjs check P02 and node CLASSROOM_RC6/kit.mjs observe P02. The supplied observer compiles once, then evaluates numeric, string and inherited cases. Predicate details may still fail P02.strict-leaf at this stage; a callable result alone does not establish correct comparisons.

Trap, recovery and continuation. If valid compilation throws on every non-matching record, locate whether a record result has been confused with invalid configuration. Preserve compile-time validation and defer record matching to the returned predicate. Repeat one accepted definition across two records. Continue when the configuration is established at creation and the returned value is reusable without regenerating code.

3. Evaluate strict own-field data

Input and action. For each record received by the predicate, inspect ownership of the named field. equals uses exact comparison. atLeast requires the actual field to be a finite number before comparing it with the threshold. Predict true for own estimate 4 at threshold 3, false for own "4", inherited 4, Infinity or a missing field.

Why this changes the result. Lookup can find a prototype value without proving that the record supplied it. Numeric comparison can coerce a string without proving it meets the accepted type. C03’s Property and Value lenses locate these independent boundaries. With equals, own active:false is legitimate and differs from the string "false".

Observe and check. Run node CLASSROOM_RC6/kit.mjs check P02, node CLASSROOM_RC6/kit.mjs observe P02 and node CLASSROOM_RC6/PROBE.mjs P02-boundary. Inspect the own/string/inherited contrast; the observer’s numeric/string/inherited fields are actual predicate results, not grades.

Trap, recovery and continuation. If inherited estimate returns true, compare Object.hasOwn with the value returned by lookup and add the missing own-field decision. If string estimate returns true, inspect coercion before comparison. Repeat own number, own string and inherited number after the minimal correction. Continue when each false is explained as non-matching record data rather than an invalid definition.

4. Reuse and challenge the predicate

Input and action. After saving, run node CLASSROOM_RC6/kit.mjs check P02 and node CLASSROOM_RC6/kit.mjs observe P02 again. Expected final outcome is both P02 assertions passing. For your own external case change the field, threshold or synthetic value meaningfully while retaining the own/inherited contrast; predict each outcome before execution.

Why this changes the result. Conceptual change: “rule is code to execute” meets the unknown operator and strict numeric counterexamples. The corrected model treats a rule as a description in a closed language: compilation accepts its definition, then evaluation tests a record. This transfers to configurable filters without treating input data as programs.

Observe and check. Record one rejected definition beside one accepted definition whose record yields false. Those observations distinguish TypeError at creation from an ordinary false result. If a failure is swallowed, restore the appropriate boundary instead of widening the admitted language. Recheck the relevant invalid definition followed by the full P02 check.

Trap, recovery and continuation. Continue when the same predicate is reusable and your own discriminant is independently observed. Reflection: What is decided when the rule is compiled and what is checked when the returned predicate receives a record? This implements one leaf, not the historical recursive rule engine.

Progressive hints — open only when needed
  1. Compiling a definition and testing a record are different stages. A bad definition should not produce a silently always-false predicate.
  2. Accessing a property can find a prototype value. Ownership needs a separate check.
