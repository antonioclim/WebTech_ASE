00–02 min · Boundary

A plausible result can still be wrong

A small business record crosses a boundary. Read its accepted types before trusting a familiar-looking calculation. Today we explain one result, one repair and one limit.

const record = { active: "false", estimate: "3" };
Boolean(record.active);
0 + record.estimate;
Predict before reveal

Does either expression establish that this record is valid?

Worked explanation — not a test log

No. The results are true and "03". The operations run, but they do not enforce a boolean field or a finite numeric estimate.

C03 is synchronous. Modules, network requests and scheduled execution belong to the following week.

05–08 min · Value

A binding is not a type declaration

The application supplies the contract. typeof is useful, but a null check, Array.isArray and callability answer different questions.

typeof null          // "object"
typeof []            // "object"
Array.isArray([])     // true
typeof (() => 1)      // "function"
Predict before reveal

Is null an object value merely because typeof returns "object"?

Worked explanation — not a test log

No. null is a primitive. JavaScript has seven primitive types: string, number, bigint, boolean, undefined, symbol and null. Arrays and callable functions participate in the object system.

Preparation covers the complete inventory. Canonical example 01 provides the executable classification.

08–11 min · Value

Conversion does not validate a field

For this teaching boundary, amount must already be a non-negative finite number in an own field of an ordinary record. Numeric-looking text is rejected, not repaired silently.

typeof row.amount === "number"
Number.isFinite(row.amount)
row.amount >= 0
Object.hasOwn(row, "amount")
Predict before reveal

Compare 3, "3", NaN and -1 against that contract.

Worked explanation — not a test log

Only numeric 3 passes. The record must first be non-null, object-valued and not an array. Conversion is a separate policy, not evidence of valid input.

This is a narrow teaching contract for synthetic records, not a universal validation library. Source: Number.isFinite; canonical concepts 7 and 12.

11–14 min · Property

A returned value does not prove ownership

Lookup can delegate. In this ordinary writable-data-property example, assignment adds an own property to the extensible receiver; it does not rewrite the prototype.

const defaults = { priority: "normal" };
const job = Object.create(defaults);
job.id = "j-1";
Object.hasOwn(job, "priority"); // false
job.priority = "urgent";
Predict before reveal

What are job.priority and defaults.priority afterwards?

Worked explanation — not a test log

"urgent" and "normal". Object.hasOwn(job, "priority") is now true. Accessors, non-writable properties and non-extensible receivers require separate analysis.

Canonical example 02. Property existence is not field-type validation.

14–16 min · Identity

const protects the binding, not the record

An alias is another route to the same object. A mutation through either route changes that one shared object.

const job = { id: "j-1", priority: 1 };
const alias = job;
alias.priority = 2;
job === alias; // true
Predict before reveal

Can job.priority change even though job was declared with const?

Worked explanation — not a test log

Yes: it is now 2. The binding was not replaced. Separately created equal-looking literals would still have distinct identities.

Rebinding, container mutation and nested mutation are different operations.

16–19 min · Identity

A new array can contain the old records

Spread copies the array container. The contained references still point at the original records.

const jobs = [{ id: "j-1", priority: 1 }];
const copy = [...jobs];
copy !== jobs;          // true
copy[0] === jobs[0];    // true
Predict before reveal

Would assigning copy[0].priority = 2 leave the original record unchanged?

Worked explanation — not a test log

No. The record is shared even though the arrays differ. A before/after value check and a reference comparison establish different facts.

Canonical example 03. Array-copy evidence alone is insufficient for record independence.

19–22 min · Identity

The nested object must actually exist

Use a self-contained fixture. Two absent properties both yielding undefined are not evidence of a shared nested object.

const claim = { id: "c-1", supplier: { city: "York" } };
const copy = { ...claim };
copy !== claim;                          // true
copy.supplier === claim.supplier;         // true
copy.supplier.city = "Leeds";
Predict before reveal

What is claim.supplier.city after the last line?

Worked explanation — not a test log

"Leeds". Both records point to the same defined supplier object. The top-level copy did not duplicate that nested object.

Derived fixture D03. Observe supplier before mutation and use a fresh fixture for every trial.

22–24 min · Identity

Copy the path you intend to change

A bounded update replaces the record and the nested object on the changed path. It need not claim to clone every possible object in memory.

const claim = { id: "c-1", supplier: { city: "York" } };
const updated = {
  ...claim,
  supplier: { ...claim.supplier, city: "Leeds" }
};
Predict before reveal

Which values and identities distinguish this update from the previous mutation?

Worked explanation — not a test log

The original city remains "York". The updated city is "Leeds". Both the record and its supplier have new identities.

This is a path-specific copy for ordinary data objects. It is not a generic deep-cloning algorithm.

24–27 min · Function

Receiver comes from the call site

A regular method can be found by prototype lookup and still receive the calling object as this. Extracting the function removes that method-call form.

"use strict";
const job = { id: "j-1", describe() { return this.id; } };
job.describe();             // "j-1"
const describe = job.describe;
describe.call(job);         // "j-1"
Predict before reveal

What does a bare describe() do in this strict-mode example?

Worked explanation — not a test log

It throws TypeError when it tries to read id from undefined. The callable value still exists; its call no longer supplies job as the receiver.

Bounded strict-mode example. Do not generalise a browser top-level this result to every execution context.

27–30 min · Function

Configuration time is not evaluation time

A factory validates configuration once. Its returned predicate reads that retained binding for each later record. Here record amounts have already passed validation.

const makeMinimum = (minimum) => {
  if (!Number.isFinite(minimum)) throw new TypeError("minimum");
  return (claim) => claim.amount >= minimum;
};
const atLeast10 = makeMinimum(10);
Predict before reveal

What does atLeast10({ amount: 12 }) return? Where did 10 come from?

Worked explanation — not a test log

true. The returned function closes over minimum from the factory call. It does not obtain 10 from this and it does not convert the record amount.

Derived D04. The record-type precondition is separate from configuration validation.

30–32 min · Function

A function is a value with a call contract

filter receives a predicate. map receives a projection. A function can be passed or returned without executing it at that moment.

const twice = (x) => x * 2;
const apply = (operation, value) => operation(value);
apply(twice, 3); // 6
Predict before reveal

Should every method be replaced with an arrow function because it is shorter?

Worked explanation — not a test log

No. Arrow functions retain lexical this; they do not receive a new dynamic method receiver. Choose the required semantics rather than the shorter spelling.

Arrow/constructor detail is transfer material. Not every non-arrow callable is constructible.

35–38 min · Shape

Read the fixture before the chain

These synthetic claims already satisfy the stated field types. The selected set is defined by approved === true. Different selection rules answer different questions.

const claims = [
  { id: "c-2", approved: true, amount: 8 },
  { id: "c-1", approved: true, amount: 3 },
  { id: "c-3", approved: false, amount: 20 }
];
Predict before reveal

Which two identifiers should enter the view, and what should their total be?

Worked explanation — not a test log

c-2 and c-1 enter the view. Their total is 11. The rejected amount 20 must not enter a summary of selected claims.

38–41 min · Shape

Projection and ordering do different jobs

Projection chooses the fields of a view. Ordering should name the array being rearranged and the key being compared.

const views = [
  { id: "c-2", amount: 8 },
  { id: "c-1", amount: 3 }
];
const ordered = [...views].sort((a, b) => a.amount - b.amount);
Predict before reveal

Are views reordered? Are ordered and views record-independent?

Worked explanation — not a test log

views retains its order because a different array is sorted. The record objects are still shared. The ordered amounts are 3 and 8.

Array.prototype.sort rearranges its receiver. This does not imply that the comparator or record fields are always side-effect free.

41–44 min · Shape

Give the accumulator a contract

The total is numeric, begins at 0 and adds only validated numeric amounts. The initial value also defines the empty-input result.

const views = [{ amount: 3 }, { amount: 8 }];
views.reduce((total, view) => total + view.amount, 0);
[].reduce((total, view) => total + view.amount, 0);
Predict before reveal

What should the two results be? What changes when "3" replaces 3?

Worked explanation — not a test log

The results are 11 and 0. A string can change + from numeric addition to concatenation. A reducer does not validate the record merely by iterating it.

Canonical concepts 30–32. An initial value does not make malformed non-empty data valid.

44–46 min · Effect

Check the population being summarised

An accurate sum of the wrong population is still the wrong business result. Label the stage supplying the summary and preserve a before/after input observation.

all amounts:       8 + 3 + 20 = 31
selected amounts:  8 + 3      = 11
ordered view:      3, 8
Predict before reveal

What does seeing total 11 fail to prove?

Worked explanation — not a test log

It does not prove that the original array was preserved, that output records are independent or that invalid inputs are rejected. Those need separate checks.

One passing observation supports one bounded claim, not every contract at once.

46–49 min · Value → Shape

Trace the actual "035" mechanism

This is the canonical generated-code audit fixture. Truthiness admits the string "false". The reducer begins with numeric zero, then string addition changes its type.

const rows = [
  { active: true, estimate: "3" },
  { active: "false", estimate: 5 },
  { active: false, estimate: 8 }
];
// accumulator: 0 → "03" → "035"
Predict before reveal

Is the mechanism true + "3" + 5?

Worked explanation — not a test log

No. The accumulator starts at 0. true controls selection of the first row; it is not the accumulator. The third row is filtered out.

Canonical example 05. A plausible explanatory comment must still match the executed expression.

49–52 min · Effect

Preserve the failure that distinguishes the cause

The supplied audit example distinguishes a non-boolean active field from a non-numeric or out-of-range estimate. A boundary records the row index and the specific issue.

row 0 → RangeError: invalid estimate
row 1 → TypeError: active must be boolean
row 2 → accepted, inactive
valid active total → 0
Predict before reveal

Why is catch { return 0; } an inadequate repair?

Worked explanation — not a test log

It collapses invalid input and a valid zero result. Catch only where the caller has a policy for reporting, skipping or stopping.

These categories describe the supplied example. Do not rename its actual RangeError to match a preferred convention.

52–54 min · Identity → Effect

Do not invent the second defect

An unsafe function can sort an input array in place and then map each element to a new record. The mutation claim and output-alias claim can have different verdicts.

const items = [{ id: "b" }, { id: "a" }];
const before = items.map(x => x.id);
items.sort((a, b) => a.id < b.id ? -1 : a.id > b.id ? 1 : 0);
const output = items.map(x => ({ id: x.id }));
Predict before reveal

Can this example mutate the array yet return fresh records?

Worked explanation — not a test log

Yes. The input order changes from b,a to a,b. Each mapped record is new. A report claiming output-record aliasing would need a different witness.
