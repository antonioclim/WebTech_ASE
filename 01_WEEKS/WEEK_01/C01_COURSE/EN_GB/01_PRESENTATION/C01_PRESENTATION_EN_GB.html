Follow one exchange, then bound the claim

Today we will follow one web exchange from the client’s request to the server’s response. You will identify what each message contains, use those facts to support a claim and name the evidence still missing. By the end, you should be able to annotate a POST response, separate URL components and propose a check that could contradict an overconfident conclusion. The examples below are demonstrations and retrieval practice, not another assessed project.

What can we observe at each boundary?

Who owns each part of the route?

A click is an interface event. Client code decides whether to send a request; the HTTP client constructs and transmits a message. A listener receives it, routing chooses an operation and application rules decide how to respond. Storage is a further boundary: a response seen in the browser does not itself show a storage write. Draw an annotation at the boundary where your evidence actually appears.

Roles change with the exchange

A resource is not its representation

Resource

Representation

HTML · JSON · text

Metadata

Content-Type · ETag · Content-Language

One identity can have several representations

The resource is the thing identified, such as claim EC-2048. A representation is content describing it, such as the shown JSON object or a possible HTML view. Content-Type declares the representation’s media type, meaning the type of content the recipient should interpret. A .json suffix suggests a convention but is not the response declaration. Compare the same JSON-looking bytes under application/json and text/plain: their appearance matches, while the declared interpretation differs.

12–16 min · URL

A URL has components with different destinations

https://shop.example.test:443/claims/EC-2048?view=compact#history

Scheme: https · Host: shop.example.test · Port: 443 · Path: /claims/EC-2048 · Query: view=compact · Fragment: history

The fragment stays at the client; it does not cross the HTTP boundary.

Parse the address before interpreting it

The scheme chooses an addressing protocol; host and port select the authority; path and query form the request target in this example. The fragment identifies a client-side position and is omitted from that target. Example 01 parses an address without contacting its fictional host. Predict what owner=Ada%20Lovelace becomes through searchParams: the decoded query value has a space, while the transmitted query text retains percent encoding.

Path, query and body occupy different parts of an address or message. A query often carries selection criteria, but the endpoint defines what topic=css means: URL syntax does not mandate filtering. 23–27 min · response

A response is a contract, not a green colour

HTTP/1.1 201 Created
Location: /api/claims/EC-2048
Content-Type: application/json

{"id":"EC-2048","status":"submitted"}

Status, headers and body must be interpreted together.

The response is a separate message

The server reports 201 Created and identifies the declared created resource with Location. Its response Content-Type describes the returned body. The request and response may both declare JSON, but they describe different content. For the illustrated exchange, say “the server reported creation of EC-2048”. Approval, payment and durability require observations of those separate business or storage boundaries.

The method communicates intent

MethodIntentDoes not guarantee
GETretrieve a representationthat the server has no internal effect

Intent is distinct from implementation activity

GET requests retrieval and has safe intended semantics; incidental logging does not change its stated purpose into creation. POST asks the target to process submitted content according to its rules and may create, calculate or reject. Therefore “POST always means a new record” is a poor prediction. The actual status and endpoint contract tell you which outcome was reported.

Use the precise status, then read its context

Matches the JSON API contract

application/json + valid JSON

Agreed contract: this endpoint returns application/json. JSON-looking bytes alone do not establish that declaration.

Separate declaration, syntax and contract

Three questions need different checks: what media type is declared, whether the content parses according to that type and whether the resulting value meets the endpoint contract. text/plain with braces can be valid HTTP text while failing an agreed JSON API declaration. application/json with “not json” declares JSON but fails parsing. A charset parameter does not change the base media type in these examples. This inspector does not promise general negotiation or every +json suffix.

A missing response leaves an uncertain outcome

A client can lose a response after the server processed a request. A retry may repeat the same intention; two deliberate clicks may represent different intentions. An idempotency key is a value used by a declared server policy to recognise a repeated operation. The policy must specify scope, retention and conflicting input handling. Merely sending a header does not implement it. Neither supplied C01 server demonstrates such a policy.

C01 · discriminating HTTP demonstration

Fresh POST text is not a durability witness

Before execution predict the later GET if the server simply echoes POST content and returns a fixed object for GET. These two hypotheses differ: “POST stored the new text” predicts the new text on retrieval; “POST echoed it” permits a fixed old text.

node 04_CANONICAL_EXAMPLES/02-request-response-anatomy/evidence-boundary.mjs

Run from the C01 EN_GB package root. Expected: POST 201 with “C01 fresh text”, followed by GET 200 with “Read diff”. The script prints the actual origin and both exchanges and closes its owned listener. Inspect the source to explain the absence of persistence; do not add a database to repair a demonstration whose purpose is that limit.

What the observation can establish

The differing texts contradict the particular claim that this GET retrieves the posted text. Source identifies the cause: a literal GET object and an echoed POST object. This finite experiment is not a general proof about durability. For a real storage-backed application, an independent lookup and restart observation would be needed to assess persistence. The automated demonstration is Node loopback HTTP; a browser Network trace requires its own native execution.
