C14 — Follow the claim through its evidence frontier

The continuing checklist case starts with an ambiguous claim: “creation works and the application is ready”. A useful review splits this into assertions that can fail independently. The title may be valid while saving is discarded. The repository may contain the record while the HTTP status is wrong. A build may exist while start is blocked. Each statement needs a witness at the mechanism it names.

A witness supports a bounded conclusion only when it could distinguish the relevant defect. Copying an expected title twice produces two fields with one origin. Reading the repository with the actual created ID introduces another origin. P01 uses this distinction in a real local service/repository execution. P03 keeps the quality of the conclusion separate from the truth and completeness of the evidence supplied to it.

Returned and stored have different origins

The supplied checklist adapter validates the title and calls repository.save. Under missing-persistence, the method returns a cloned record without retaining it in the Map. This is why an apparently successful command can coexist with an absent follow-up. Predict the difference before running your own target. In P01, the newly returned ID joins the two observations; a fixed ID would allow unrelated state to masquerade as the effect.

Handle absent state before title access. null is information about the lookup outcome, not a title to coerce into text. Match the returned contract fields without editing the adapter or fixtures. The adapter owns trimming, validation and its stored copies. Your witness owns orchestration and interpretation. No complete assessed implementation is supplied in this reading.

Conceptual shift. Initially, the returned record seems proof of storage. The discarded-save case leaves the response plausible and lookup absent. The corrected model separates the command result from the independently read state. Transfer to HTTP requires an actual follow-up route and ownership policy; transfer to durable storage needs a restart or other declared storage boundary. Neither follows from the Map result alone.

Sensitivity is a relationship between fault and observation

A witness detects a defect because that defect can change the value it reads. For missing saving, an independent find is directly connected to the altered effect. A title-only assertion has no path to that effect. For a wrong HTTP status, reading a Map is insufficient: send the actual request and inspect status. For keyboard focus, use the native browser. The minimal sufficient frontier changes with the claim.

Baseline, objective and regression are roles, not interchangeable green labels. Initial baseline success confirms the expected carrier conditions. Intended objective assertion failures locate unfinished work. A regression witness protects a stated behaviour or exposes a relevant fault. Crashes, unfamiliar assertion identities and timeouts require diagnosis. During staged implementation a whole objective can still fail because later decisions remain TODO; retain the local evidence and identify the unfinished part.

A performance number needs a denominator and a clock

Our fixed model stipulates 200 completions in 4 seconds. Division produces 50 per second. It is not measured production capacity. Concurrency counts current work in flight and cannot replace either numerator or denominator. Name which outcomes count as completions: success, HTTP failure, transport rejection and local timeout are different observations. A local timeout says that local waiting ended, not that remote execution stopped.

For latency, name when the timer starts and stops. Headers at 12 ms and body complete at 48 ms illustrate two different intervals under stipulated times. If usable body is the claim, the later boundary matters. Warm-up, initial state, sample count, timeout and environment belong to the scenario before calculating a statistic.

For nine 10 ms values and one 200 ms value, the mean is 29 ms. Nearest-rank p95 uses ceil(0.95 × 10), one-based rank 10, so it selects 200 ms. Declare that algorithm and finite population. A percentile does not enlarge the evidence class of synthetic input. Historical performance P02 remains an optional course example; there is no current S14 P02 and no added benchmark obligation.

A public observation must preserve meaning without leaking context

A log records an event; a metric aggregates numbers; a trace connects operations. Selecting allowed keys limits the schema, while validation and redaction limit their values. A raw error or request body may contain secrets even if placed under a harmless-looking key. Route templates and bounded outcome labels control cardinality; an identifier useful for correlating restricted logs may create one metric series per request.

Before copying evidence, follow each value to its recipient. Keep private submission identity in the permitted private record. Use synthetic examples in AI critique and public teaching output. Redact secrets and unnecessary personal data without erasing the diagnostic meaning or evidence locator. A course projection example is source/model evidence, not a review of a live logging pipeline.

Review completion does not force readiness to PASS

The human inventory has ten named categories: PROJECT_IDENTITY, LOCKED_INSTALL, DEPENDENCY_AUDIT, PRODUCTION_BUILD, RUNTIME_HEALTH, LOG_REDACTION, CONFIG_SECRETS, HTTP_ERROR_HEADERS, DEPLOYMENT and EXCEPTIONS. For each, record claim, source/locator, state, owner, next action and limit. Only DEPLOYMENT is nonblocking in this classroom policy, but it remains visible.

P03’s short BUILD/AUDIT fixtures exercise the computation, not the authenticity of a complete review. A duplicate or missing category can leave the human review incomplete while the restricted function returns PASS. The function must preserve the input rows rather than remove inconvenient evidence. FAIL dominates required unknown; otherwise required unknown preserves UNKNOWN; otherwise PASS is scoped to supplied rows.

A scanner that failed to start leaves its category unknown. A successful build does not supply start, health or shutdown observations. LOCKED_INSTALL concerns the reviewed project when it has dependencies: it does not make npm a prerequisite for the dependency-free Map witness. A truthful complete ten-category analysis may conclude UNKNOWN. Omitted categories, incomplete target work or an unfinished independent check remain unfinished classroom activity.

Change safety reaches beyond one function

Map a wider change through route, identity, state, commit, event and cleanup. In a transactional system, publishing before a failed commit may announce nonexistent state. A successful commit followed by delivery failure leaves storage present and notification pending. A retry or outbox needs its own policy; ordering does not make an external effect atomic with the database. The seminar’s Map supplies no transaction or event bus.

One genuine AI critique can challenge a bounded assumption in this map. Its output is a claim to check independently. Record the actual prompt, actual relevant response, your separate observation and a justified accepted/rejected/partly accepted/unknown conclusion. A prepared example is not an exchange. If access is unavailable, preserve the actual blocker and continue independent work under the lecturer’s completion procedure.

Retrieve, then compare the reasoned answer

Create returned the expected title. Which additional observation exposes missing storage?

An independent repository.find with the newly returned ID can return null while create still returns the title. Copying the create result again adds no independent source. In this seminar, the observation belongs only to the supplied in-memory repository.

An audit failed to start. Why is zero findings unjustified?

No executed report exists for the claimed tool scope. Keep unknown, the real blocker, owner and next action. This honest conclusion can belong to a completed review without promoting the reviewed project to readiness PASS.

If commit succeeds and delivery fails, what remains?

Under the declared transaction model, stored state can exist while event delivery remains pending. A retry/outbox policy addresses that different obligation. The answer describes a model, not a Map durability observation.

Across C01–C14, a meaningful observation keeps identity, ownership, state and frontier together. Write the claim, predict a defect that could make it false, choose the sufficient witness and preserve a failed or unknown result. In S14, complete both individual projects, the ten-category inventory, your reflections and one genuine critique in one private PDF. Further work needs a new claim and witness; this course creates no S15, new grade, deadline or deployment requirement.

C14 — Testing, Observability, Performance and Production Evidence

A source-aligned synthesis handout. The worked companion expands each mechanism; every conclusion remains no broader than its evidence.

Readiness and test boundaries

1. Unit tests isolate local rules

Use a unit boundary for pure rules such as validation, reducers and parsers when collaborators are not part of the claim.

Evidence boundary. Test boundaries and cheapest sufficient witness; no broader runtime or deployment claim follows.

2. Integration tests join real collaborators

Use integration evidence when the claim joins real collaborators such as repositories, constraints, queues or adapters.

Evidence boundary. Test boundaries and cheapest sufficient witness; no broader runtime or deployment claim follows.

3. API tests verify HTTP contracts

Use a loopback API boundary for method, status, headers, body, persistence and public failure contracts.

Evidence boundary. Test boundaries and cheapest sufficient witness; no broader runtime or deployment claim follows.

4. Browser tests verify browser-owned behavior

Use a real browser when focus, navigation, storage, Worker, Service Worker or iframe lifecycle owns the behaviour.

Evidence boundary. Test boundaries and cheapest sufficient witness; no broader runtime or deployment claim follows.

5. Use the cheapest sufficient boundary

Choose the lowest boundary that can observe the claim. Higher boundaries add lifecycle cost and additional failure modes.

Evidence boundary. Test boundaries and cheapest sufficient witness; no broader runtime or deployment claim follows.

Performance evidence

15. “Fast” needs a scenario

A performance claim requires a declared operation, state, warm-up, sample size, concurrency, timeout, interval, statistic and environment.

Evidence boundary. Performance scenarios, concurrency and tail latency; no broader runtime or deployment claim follows.

16. Concurrency is not throughput

Concurrency is in-flight work. Throughput also needs completions and scenario duration.

Evidence boundary. Performance scenarios, concurrency and tail latency; no broader runtime or deployment claim follows.

17. Bound concurrent work

Bound scheduling and settle every operation once. Unbounded Promise.all is not a load methodology.

Evidence boundary. Performance scenarios, concurrency and tail latency; no broader runtime or deployment claim follows.

18. Classify HTTP and transport outcomes

HTTP failure, transport rejection and local timeout are distinct classes even when the client API fulfils the promise for HTTP 500.

Evidence boundary. Performance scenarios, concurrency and tail latency; no broader runtime or deployment claim follows.

19. Measure the intended interval

Header-arrival and body-complete latency are different intervals. Measure the interval named by the claim.

Evidence boundary. Performance scenarios, concurrency and tail latency; no broader runtime or deployment claim follows.

20. Mean can hide tails

A mean can conceal a severe tail. Report distribution and failures, not a single reassuring average.

Evidence boundary. Performance scenarios, concurrency and tail latency; no broader runtime or deployment claim follows.

Ownership, maintainability and AI change safety

34. Findings need ownership

Each finding needs a stable rule, severity, evidence, owner, action and any scoped exception with expiry.

Evidence boundary. Ownership, maintainability, AI impact and readiness argument; no broader runtime or deployment claim follows.

35. Maintainability is change safety

Maintainability is the capacity to change safely across responsibilities, contracts, cleanup and dependencies.

37. Commit/event ordering matters

38. Production readiness is an argument
