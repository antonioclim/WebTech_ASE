Exercise Specification — Persistence Bug Hunt

Unit

Unit 06 — Persistence with Sequelize and SQLite

Learning objective

Diagnose a plausible generated Sequelize boundary and repair model constraints plus asynchronous write/error ownership without rewriting supplied application or legacy evidence.

Why this exercise exists

Generated ORM code often appears correct on the happy path while allowing invalid rows, returning before writes settle or catching nothing because a promise was not awaited. Students need to connect model metadata, database state, promise settlement and public failures from evidence.

Prerequisites

  • Persistent Notes API and Query API.
  • Sequelize models/validation, async rejection behaviour and centralised API errors.

Starting context

Students receive a small reservation service with fixed Express routes, serialiser/error middleware, deterministic SQLite harness, tests and an intentionally preserved src/unsafe-generated-persistence.js. The unsafe module defines nullable/weak fields and returns model.create(...) from inside a non-async try/catch, so validation/database rejections escape its intended translation.

The reference repair is confined to src/persistence-repair.js, exporting defineReservation(sequelize) and createReservation(Reservation, input). A supplied compatibility branch can delegate to the unsafe module when objective repair code is absent; that branch is common to reference/student trees and clearly labeled as defective evidence.

Reservations have public fields id, code, guestName, seats, createdAt and updatedAt.

Required behaviour

  • Define code as a non-null unique string, trimmed and restricted to ^[A-Z0-9-]{4,16}$.
  • Define guestName as a non-null string whose trimmed value is nonempty; persist the trimmed value.
  • Define seats as a non-null integer with minimum 1 and maximum 8.
  • Keep integer auto-increment primary key and Sequelize timestamps.
  • createReservation is async, awaits Reservation.create and returns a detached plain object only after persistence succeeds.
  • Sequelize validation failures are caught and rethrown as PersistenceValidationError with code: 'reservation_invalid' and a stable non-sensitive message.
  • Unique-code database/constraint failures are caught and rethrown as PersistenceConflictError with code: 'reservation_exists'.
  • Unexpected failures propagate unchanged to centralised internal-error handling.
  • Invalid/conflicting writes insert no row, produce no unhandled rejection and settle before the request handler responds.
  • The preserved unsafe module remains byte-for-byte unchanged and is never used by the validated reference path.

Constraints

  • JavaScript ESM, Sequelize stable 6.x, SQLite, Express 5 supplied code, native fetch and Node's test runner.
  • Edit only src/persistence-repair.js; do not edit the unsafe generated module, routes, error middleware, tests or dependencies.
  • Do not validate only in Express; constraints must exist in model metadata and direct model/store checks.
  • Do not swallow unexpected errors, match database errors solely by message text or add a second model/table.
  • Tests use isolated temporary/in-memory databases and deterministic cleanup.

Observable completion criteria

  • The initial student checks expose nullable/format/range/unique defects and escaped asynchronous rejections while baseline server/model evidence remains inspectable.
  • After repair, all categorized checks pass and only src/persistence-repair.js differs.
  • Model metadata and direct invalid writes prove constraints independently of HTTP validation.
  • Duplicate and invalid API requests return stable 409/400 errors; unexpected failures return sanitised 500.
  • No unhandledRejection is observed and successful responses occur only after the row is queryable.
  • The student can explain why return Model.create() inside a synchronous try block does not catch a later rejection.

Validation plan

Baseline checks

  • Supplied Express/server/error lifecycle and deterministic database harness work with a known safe fake.
  • The unsafe module remains present, unchanged and reproducibly demonstrates weak metadata plus escaped promise rejection.

Objective checks

  • Model metadata and direct writes enforce non-null, format, normalisation, integer range and uniqueness.
  • Successful creation returns a detached object only after the row exists.
  • Invalid/duplicate failures become the exact custom errors and insert nothing.
  • An injected unexpected failure preserves object identity for centralised handling.
  • A rejection observer records no unhandled promise for repaired calls.

Regression checks

  • Malformed JSON, unknown routes, health and database cleanup remain healthy.
  • Failed writes do not poison a later valid request.
  • Public bodies expose no SQLite SQL, stack, storage path or raw constraint text.
  • The unsafe evidence module is identical across reference/student and excluded from the repaired runtime path.

Intended student work

Use the completion and validation criteria above to justify your implementation. Keep the originally supplied incomplete target identifiable before your first edit.
