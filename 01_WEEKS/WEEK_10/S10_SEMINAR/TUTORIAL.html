P01-01 · Map the event and the authorised field

Starting state and prediction. Read workshopTransition({state,action}) in CLASSROOM_RC6/student/p01.mjs. Imagine a workshop list with a track filter and saved sessions. Track selection changes what is shown; saving changes the shared accepted selection. Before editing, write a table for track/selected, session/toggled and saved/cleared: previous values, event payload, permitted change and values that must survive. Predict selecting data from a state that also has sort:"title" and an existing saved ID.

Action and mechanism. The event authorises a particular change, rather than permission to reconstruct only the fields you remember. Inspect C10 canonical example 02: its reducer changes enabled or seats inside a component-owned useReducer. The reducer makes an event policy inspectable; it does not itself make that owner application-global. Your function receives state explicitly and does not mount that component. C10 canonical example 01 shows another legitimate coordination mechanism: common App state passed to children through values and callbacks.

Change and observable. Write your own first track-selection decision in the TODO target and save. Run node CLASSROOM_RC6/check.mjs work from the EN_GB directory described below. Read the P01 named assertion even while P02 and P03 remain unfinished. The selected track must change, while saved IDs and the extra sort value keep their content. The earlier input must still describe its previous state. A null TODO is unfinished. A check result is finite function evidence, not a rendered workshop filter.

Trap, diagnosis and recovery. Returning only track and savedIds may pass a two-field example yet discard another consumer’s sort preference. A shallow outer copy also does not authorise changing the earlier savedIds array. If an extra field disappears, compare every input field with your event table and locate the reconstruction. If the prior input changes, inspect the write destination. Recover in the target, preserve the original failing result and rerun the same fixture. Do not weaken the protected support case.

Record, reflection and continue. Keep the prediction, changed decision, actual CWD/command and result. Explain which event authorises the changed field and which consumers would lose information if another field vanished. Continue when the table and track case agree. Course bridge: ownership before mechanism. The conceptual shift is from “return some plausible state” to “account for every authorised change and preserved value”.

P01-02 · Trace both toggle branches

Starting state and prediction. Use a state containing saved IDs alpha and beta. Predict toggling alpha, then predict toggling gamma from the same previous state. Finally predict two deliberate gamma toggles in sequence, using the first result as the next state. These are distinct events, not duplicate seed records. A present ID is removed; an absent ID is added. The full earlier content and track remain available.

Action and mechanism. Analyse membership before choosing the next saved collection. Removal must leave unrelated IDs; addition must retain earlier IDs. C03 immutable-array reasoning matters because changing a nested array would change the earlier snapshot even when the surrounding object was copied. The contract concerns content preservation and input immutability. It does not demand universal deep cloning or a particular identity for every unaffected object. Seed normalisation and event deduplication answer different questions: this API has no event-ID ledger.

Change and observable. Implement your two branches and run the work check. Its protected P01 cases include a non-empty absent-ID addition and removal. Design a distinct private fixture with two earlier IDs and an opaque new one, save it outside the collection and run the P01 try command below. Compare actual output with your prediction and input_unchanged. For the two-event contrast, make the second JSON state from the first actual result, predict again and record both runs; do not call the first prediction an observation.

Trap, diagnosis and recovery. A branch that only removes can look correct on the original present-ID fixture. Using push or splice on input can produce convincing final JSON while corrupting the earlier state. If the addition loses an earlier ID, inspect the source array. If the two toggles leave gamma present, examine whether you accidentally treated repeated intentional events as deduplicated input. Recover by restoring the original fixture, separating present and absent decisions and repeating the protected check and both sequential personal runs.

Record, reflection and continue. Continue when both branches preserve the previous input and two deliberate toggles restore the prior saved content. Explain why a repeated seed ID is not a repeated user event and why your finite case does not prove provider isolation. Record a personal falsifier for a remove-only implementation. Reflection: what other reader could observe a mutation to the earlier array?

P02-01 · Separate matching ownership from success

Starting state and prediction. Read notificationRefresh({owner,reply,success,items,received}) in p02.mjs. Owner identifies the refresh currently permitted to publish; reply identifies arriving work. IDs are opaque labels, not timestamps or alphabetic freshness. Build four rows: matching/successful, matching/failed, different/successful and different/failed. Predict which list each row may publish before calculating any count.

Action and mechanism. Ownership and success are independent necessary conditions. A matching failed reply has no successful replacement; a successful old reply has no current authority. S09’s simpler publication model assumed a successful result, while this S10 interface supplies success explicitly. C10 canonical example 05 records currentRequestId on pending and checks it on fulfilled, but has no rejected handler and uses a local timer rather than HTTP. It illustrates one success path, not all four rows of this function.

Change and observable. Implement your own acceptance decision, keeping input unchanged. Run the P02 objective via the full work command. Its four-row contrasts keep old and received lists visibly different. For a personal case hold IDs equal and change only success; then hold success true and change only reply. Save and run both inputs separately so you can attribute the changed result to one condition rather than to several changed values.

Trap, diagnosis and recovery. Checking only equality admits a matching failure. Checking only success admits stale work. Treating whichever result arrives last as the owner confuses settlement with permission. If the chosen list is wrong, inspect the two conditions before debugging count arithmetic. Restore a one-factor contrast, state the prediction again and change only your target. A runner exception is not a meaningful false decision or expected refresh failure.

Record, reflection and continue. Record the condition changed, actual command and chosen list. Continue when you can explain every row without relying on sample IDs. Conceptual shift: completion does not grant publication authority. Your reflection must state that this function starts no request, aborts nothing and owns no Redux store.

P02-02 · Select the authoritative list

Starting state and prediction. Predict a matching successful reply whose received array is empty. It authorises replacing a non-empty old list with empty. Compare a successful stale empty reply: the old list must remain. These outputs may look similar to unfinished or failed loading in a larger application, but this contract supplies enough information to distinguish them without guessing from list length.

Action and mechanism. Choose the complete list once from the acceptance decision. Successful emptiness is data; refusal preserves accepted prior data. Do not use truthiness of array length as a substitute for success or ownership. The returned items and later unread count must refer to the same chosen snapshot. C10’s ownership map makes this relationship explicit: a read view derives from accepted data rather than becoming a second independently synchronised authority.

Change and observable. Complete the selected-list decision. Run the protected successful-empty and stale-empty contrasts and a personal matching-failure input. Predict all item fields, including read flags. Record actual_output and unchanged-input field from try. This API need not mutate received to mark items read, merge stale lists or create a pending status. Reusing an unchanged array or returning an equal copy is compatible with content/immutability requirements here.

Trap, diagnosis and recovery. A fallback such as “if no received rows, retain items” refuses an authorised clear. Accepting an empty stale list erases current data. Merging items and received answers a different refresh contract. Diagnose the selected source before changing its representation. Recover by contrasting identical empty received arrays under matching and different reply IDs, then repeat the assertion. Do not add validation or state fields that the interface does not request.

Record, reflection and continue. Continue when empty replacement and refusal are causally distinct in your evidence. Reflection: why can an empty successful result be authoritative while an apparently richer stale result is refused? Transfer this source-selection rule to a document list without assuming it also orders a mark-read mutation or reset. Those interleavings require their own policy and witness.

P02-03 · Derive unread from the selected list

Starting state and prediction. Use old items with two unread records and received items with one read record. For a refused reply, predict old items and unread two. For an accepted reply, predict received and unread zero. Also use an accepted mixed list to predict unread one. The count concerns entries with read:false in the selected list, not stale received data and not a mutation that makes the count fit.

Action and mechanism. Calculate unread only after selecting the authoritative collection. In C10 canonical example 04, adapter-maintained IDs order entities and selectAll follows them; unread is derived from read fields. The source’s read reducer assigns true in an Immer-managed draft, so a second mark stays read. That syntax does not authorise mutation of ordinary seminar inputs. This P02 function does no marking, normalisation or memoised subscription.

Change and observable. Finish the derived count and run the full work check. The same protected P02 ID checks accepted, refused and empty cases with different counts and preserves input snapshots. Design one personal stale reply whose received count differs from the retained count. Run it and compare every output field with your prediction. Correct items with count from the refused array is still a failed contract. Do not infer actual rendered count from a Node log.

Trap, diagnosis and recovery. Storing a second count or counting received in every branch can leave a contradictory result. Counting truthy read strings would also describe another interface; these declared fixtures use Boolean flags. If items are right and unread wrong, trace the exact array counted and the read:false condition. If input flags change, locate the write. Recover using the same rejected-list contrast, preserve the failed observation and repeat after changing the target.

Record, reflection and continue. Continue to P03 when the P02 objective passes and the count can always be explained from the returned items. Record a conceptual shift from “update a badge separately” to “derive a coherent view from its accepted source”. State that the pure result proves no HTTP confirmation, React effect, Worker message or service-worker cache operation. Refresh/refresh authority alone cannot qualify refresh/mark/reset.

P03-01 · Establish every required capability

Starting state and prediction. Read chooseArchitecture({required,candidates}) in p03.mjs. Candidates declare IDs, capability arrays and nonnegative costs. Before comparing costs, write a row for every candidate against every required capability. Predict a cheap candidate that has only one of two required capabilities, then a more expensive candidate with both. A missing requirement cannot be bought with a low cost.

Action and mechanism. Determine eligibility from every required capability. An empty required array excludes nobody on capability grounds; it is not the same as no candidates. The fixture named lifted lacks shared only in that descriptor. Real lifting can coordinate siblings through a common owner and callback props, as canonical example 01 demonstrates. This is a decision over stipulated input descriptors, not a universal ranking of Context, Redux or props.

Change and observable. Implement your own eligibility reasoning and run the P03 objective. It includes multiple required capabilities and a cheaper partial candidate. Make a distinct private case with different synthetic labels and two requirements so an any-one-capability rule would be falsified. Record the reason for each exclusion before the actual output. Do not add malformed-cost rejection rules: the current input contract declares nonnegative costs and supplies no new validation policy.

Trap, diagnosis and recovery. Using some requirement instead of all allows a partial candidate to win. Choosing the cheapest candidate first then checking it can miss an eligible alternative. If a cheap partial candidate wins, inspect the order of eligibility and comparison. Restore the capability matrix, keep costs unchanged and repair only the target. If there are no eligible candidates, null is legitimate; it must be supported by a no-eligible contrast and a separate case with a winner.

Record, reflection and continue. Continue when every excluded candidate has a named missing requirement and every eligible one covers the complete required set. Reflection: which claim is supplied capability data and which would require an actual implementation test? A successful model selection cannot verify parity, performance or a framework’s inherent abilities.

P03-02 · Compare costs only among eligible candidates

Starting state and prediction. Among three eligible candidates, predict a unique minimum at cost zero with two other candidates tied at a higher cost. Zero is a declared nonnegative cost. The higher tie does not affect the unique minimum. Reverse the candidate input order and predict the same winner. State separately why a cheaper ineligible candidate remains excluded.

Action and mechanism. Compare costs within the eligible set and preserve the earlier input. Sorting a copied list is one possible strategy; mutating the supplied candidates array would break input immutability. No particular algorithm, deep copy or result object identity is mandated. The fixed course expressions cA=1+p and cB=2+0.15p are a separate arithmetic example under stipulated coefficients, not measured costs for these descriptors.

Change and observable. Complete your own minimum comparison and run the work check. Use your reversed-order personal case to distinguish a cost comparison from “first eligible wins”. Record the input order, predicted ID and actual output. An implementation that returns null for all cases might accidentally satisfy a tie case, so a distinct winner case is essential. Keep candidate IDs unchanged; do not return the whole descriptor or a library name you invented.

Trap, diagnosis and recovery. Treating any equal costs anywhere as ambiguity rejects the unique lower candidate. Sorting input in place can hide mutation because the winner still looks correct. If the winner changes under reversal, inspect order-dependent state. If input_unchanged is false, inspect sort or another write on the original array. Recover with the same finite fixture and a copied working representation or another non-mutating strategy of your own.

Record, reflection and continue. Continue when unique-minimum cases pass, reversed input preserves the answer and prior content is unchanged. Reflection: why is an assumed cost useful for a conditional decision but insufficient for an empirical architecture recommendation? Transfer by naming a workload and measurement that would be needed before making a real speed or maintenance claim.

P03-03 · Distinguish a tied minimum from no eligible candidate

Starting state and prediction. Predict two cases that both return null for different reasons: all candidates miss a requirement, or two eligible candidates share the lowest cost. Then change one tied minimum cost to make a unique winner. These contrasts distinguish a complete decision from the TODO null and distinguish two separate reasons for refusal.

Action and mechanism. Account for the number of candidates at the minimum, rather than choosing by alphabet, original order or an invented preference. A historical course model demonstrates an explicitly lexical tie policy; current S10 requires null at a tied minimum. A higher-cost tie is still harmless. Explain the contractual rule before selecting a mechanism so a deterministic output is not mistaken for a justified winner.

Change and observable. Complete your target and run node CLASSROOM_RC6/check.mjs work and node CLASSROOM_RC6/verify.mjs work. Final completion expects both baseline tests and all three named objectives to pass under the unchanged protected boundary. Save a personal genuine tie, no-eligible input and one-factor winner contrast outside the collection. Try prints actual data without grading your prediction, so record your explanation and falsifier as well as the exit.

Trap, diagnosis and recovery. A lexical tie-break copied from another model violates this contract even if it is repeatable. A null with no eligible candidates does not establish correct unique-minimum handling. Diagnose eligibility first, then the minimum and its multiplicity. Recover with a paired winner/tie contrast under unchanged capabilities. Do not change fixtures, expected outputs or boundary files to hide a failure. Runtime faults remain blocked execution, not legitimate null results.

Record, reflection and continue. Continue to the single AI critique and evidence review when all three objectives pass and you can explain every refusal or selection. Reflect on ownership, acceptance and eligibility as distinct authority boundaries. For C11, a UI role label or hidden delete button is a client view; it cannot establish a server’s trusted actor or authorised operation.
