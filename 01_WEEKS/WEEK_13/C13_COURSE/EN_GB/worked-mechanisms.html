1. A stored string becomes application state

Input and owner. The page owns the preference key webtech:preferences. The canonical contract admits version 1 and a theme of comfortable or compact. The fallback is {theme: "comfortable"}. Storage persists strings; a syntactically valid JSON string is still an unvalidated record. Local storage is associated with the origin and has no general locking guarantee. Access and writes can fail under browser policy or capacity limits. [Storage standard]

Source: 01-versioned-storage-record/main.js. The derived storage helper is a separate model: it uses density, not the canonical theme field.

  1. Read bytes. getItem(key) returns either a string or null. A missing record selects the fallback immediately; no parsing occurs.
  2. Parse. A string such as {"version":1,"theme":"compact"} becomes a JavaScript value. Parsing establishes syntax, not the permitted version or theme.
  3. Validate. Check the version and theme against the contract. An old version or an unsupported theme fails admission even if JSON parsing succeeded.
  4. Project or recover. For a valid record, return a new object containing only theme. For malformed or invalid data, remove this owned key and return the fallback. No automatic migration is implemented.
  5. Render. The page writes the admitted theme to textContent. A read decision and a display decision remain separate operations.

Limit. The canonical getItem occurs before its try, and recovery removal is outside that protected region. A storage access or removal exception is not the same as malformed JSON and is not caught by this example. Its initial demonstration also deliberately removes the preference key, so it is not a normal user-preserving application startup. Neither a fallback nor a schema check makes stored data authoritative identity.

Design choice. If version 0 must remain usable, specify a migration with an explicit input contract and resulting version. If storage is unavailable, decide whether the application may continue with an in-memory preference and how it tells the user that persistence did not succeed.

2. A Worker receives a clone

Input and owner. The page owns {values: [2, 4, 6]}, the DOM status element and the Worker lifecycle. The Worker owns the computation in its own execution context. Ordinary messaging uses structured serialisation; a clone is a separate object graph. Transfer instead moves a transferable resource, such as an ArrayBuffer backing store, and detaches the sender's buffer. Functions are not ordinary cloneable data. [Structured data] [Workers]

Source: 02-worker-clone-boundary/main.js and worker.js.

One request, two separate states
StepPage stateWorker state / result
Construct and sendvalues = [2, 4, 6]; sends the objectMessage data is serialised for the Worker
Mutate the page's objectvalues = [99, 4, 6]The message's cloned values remain [2, 4, 6]
Compute and replyWaiting for a messageReduces its values to 12; sends {total: 12}
Display and finishDisplays worker total=12; main first=99; terminates the WorkerThe one-request lifecycle ends

Why a timer is different. Deferring computation with a timer changes when the page's work is scheduled; it does not establish another Worker execution context. Offloading can reduce competing page computation, but copying, transfer, startup and coordination have costs. The example contains no responsiveness measurement.

Limit. Both message listeners are one-shot. There is no request identifier, progress schema, timeout, error handler or cancellation path. The success path terminates the Worker; a missing reply does not reach that cleanup. This is a clone witness, not a reusable Worker client.

3. Registration, readiness and control answer different questions

A registration associates a script with a scope. The ready promise resolves for a matching registration with an active worker. The page's controller identifies the worker controlling that client and can be null. These observations are not interchangeable. A controller change is also a lifecycle event for application protocols. [Service Workers standard]

Source: 03-service-worker-scope-decision/main.js and sw.js.

  1. Register. The page awaits register("./sw.js"). This is the registration operation, not a receipt that the page is already controlled.
  2. Await an active registration. It awaits navigator.serviceWorker.ready.
  3. Select the actual source branch. It chooses controller ?? registration.active. Therefore it may message an active worker when the page has no controller. The README's claim that first-load uncontrolled requests remain on a direct path is not enforced by this selection.
  4. Send a message. For each request description, the page creates a MessageChannel, transfers its second port and waits for the worker's reply on the first.
  5. Classify in the worker. The message handler starts with network. It changes that label only for a same-origin GET whose path matches one task segment.

Limit. These are labels in replies: the example does not make the classified network request, register a fetch interceptor or fill a cache. It lacks message timeouts, port cleanup and a complete payload contract. skipWaiting and clients.claim are lifecycle choices in this source, not proof that an observed page was controlled at a particular instant.

Work through an offline policy separately

Fixed design exercise. Suppose an application owns cache names beginning catalog-shell: and publishes shell version v3. Its declared offline scope is the shell and a help page; writes and live inventory remain online operations. This is a policy trace, not an implemented cache or an offline acceptance result.

  1. On installation, identify the exact shell assets required before considering the new version usable.
  2. On activation, remove obsolete caches only within the application's owned namespace; retain unrelated caches.
  3. For a navigation, apply the declared freshness and fallback policy. A cached shell may display while fresh inventory is unavailable.
  4. When a controller is replaced, define whether pending messages are rejected, retried or reconciled. Replaying a write requires an idempotency policy.
  5. To support the product claim, test the named routes and failure conditions in a controlled browser environment, including missing cache data and denied or evicted storage.

Result. “The help page remains readable under these offline conditions” is a bounded claim. “The whole application works offline” would require evidence about every promised route, asset and operation.

4. A message becomes a trusted intent only after admission

Input and owner. The parent receives a MessageEvent, not an authorised command. Its gate owns which window and origin may propose which intent. The messaging standard requires attention to origin, payload format and destination; an exact target origin restricts delivery but does not replace the receiver's checks. [Web messaging]

Source: 04-message-contract-gate/main.js, child.html and decoy.html.

  1. Compare event.origin with the configured child origin http://127.0.0.1:4217.
  2. Compare event.source with the specific catalogue frame's contentWindow. The decoy has the same origin but another Window, so origin alone would admit too much.
  3. Admit only version 1, type catalog/select and a string payload.itemId.
  4. Project to {type, itemId}. The sender's extra trusted: true claim is discarded.
  5. The parent updates its display from that intent. Any authenticated user permission decision belongs to a separate authority boundary.

Limit. Both embedded senders use the same child origin, although that origin differs from the parent. Their demonstrated distinction is source identity. The derived helper adds an identifier format and length bound but uses another envelope (item.selected); it is a comparator, not a byte-identical version of this example. Neither origin nor a sender-written flag establishes user authorisation.

5. A replacement creates a new generation

Input and owner. The shell owns a generation counter, its current frame and one queued render command. Readiness is application protocol state: a frame element's existence alone does not release the command. The canonical example deliberately keeps the old frame hidden so that it can produce a late readiness event.

Source: 05-frame-generation-gate/main.js and child.html.

State invariant. A command for generation 2 must not be released by readiness for generation 1. A late event should leave current state unchanged. The pass marker requires both an ignored obsolete ready event and the current render; timer values are an intended demonstration schedule, not a portable timing guarantee.

Limit. The parent checks source and generation but not event.origin. Generation is lifecycle correlation, not sender authentication. The old iframe remains in the document, and the listener remains installed. A reusable shell also needs removal, listener cleanup, per-type schema, duplicate policy and protection when asynchronous work outlives the generation that started it.

Combined design question. On replacement, how will the shell renew the expected source, origin and generation together, preserve only permitted queued work, and reject late completion without leaking resources? Keep the answer in a lifecycle plan; the seminar's assessed code remains a separate task.

6. Choose and own the boundary

A requirement should determine the mechanism
RequirementCandidate mechanismNew ownership costNext sufficient witness
Remember a display preferenceVersioned storage recordSchema, recovery and persistence failureStorage admission cases; then target-browser persistence
Move costly computation away from page workWorkerProtocol, pending state and terminationCorrelation/cleanup checks plus measured browser responsiveness
Apply a browser-managed request/offline policyService WorkerControl, replacement, cache and fallbackQualified control and route/failure traces
Give an independently owned document a narrow intent channelIframe compositionTrust, readiness, generation and navigationReal topology plus rejection and replacement cases

If the requirement is simply to split code for one team, ordinary modules may avoid another document and protocol. Independent ownership or isolation can justify composition, but the decision should name the parent owner, child owner, failure policy and simpler alternative.
