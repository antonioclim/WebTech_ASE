What you will do and why

Browser APIs expose different kinds of identity and readiness. You will model message acceptance, routing under controller ownership and the provenance of a frame message. Each task isolates a predicate that a complete application would need before trusting a message or choosing a delivery route.

Before you start: Use exact string/number equality, inspect object properties, parse a URL and read nested fixtures. S12’s current-request correlation and S11’s trust boundaries provide the relevant reasoning.

Observable learning outcomes

  1. Separate existence of an own result property from truthiness of its value.
  2. Require controller ownership, same origin, GET and the intended task path before selecting the controlled route.
  3. Reject a frame message whose origin, source token, schema version or generation is stale or mismatched.

S11–S13 use bounded JavaScript models. They do not run Express, a queue framework, WebSocket delivery, a native Worker, a Service Worker or a cross-origin frame boundary. A classroom PASS concerns the supplied finite contract and input immutability. It does not complete the retained full application, authenticate authorship or qualify another OS/browser.

The full required v3.0.0 route is planned for 120–165 minutes. The workload remains unpiloted; all 3 projects are required individual work. Read the full-work allocation before class.

P01 — Worker reply: own result and current ID

A reply may have a result and still belong to the wrong request. It may also have a legitimate result such as 0, false or an opaque string. Accept the correct completion message for the current ID only when the reply owns its result property.

Editable target: CLASSROOM_RC6/student/p01.mjs
Exported function: acceptWorkerResult(input)

Read the input and output contract

Input fieldMeaning

Return value: {accepted: true, result: reply.result} for a matching analysis.completed reply with an own result property; otherwise {accepted: false}. Preserve the opaque result value.

P02 — Service Worker: controlled routing predicate

Select controlled protocol only for a page that is currently controlled and a request that matches all remaining conditions. A registered or ready Service Worker is a different fact from a controller owning this page. Here controlled is an explicit synthetic flag.

Editable target: CLASSROOM_RC6/student/p02.mjs
Exported function: serviceWorkerLane(input)

Read the input and output contract

Input fieldMeaning
controlledBoolean modelling current controller ownership.
originThe page’s origin string.
urlAn absolute synthetic request URL, with origin and pathname to inspect.
methodThe request method; only GET fits this controlled task-route contract.

Return value: The string controlled only for controlled, same-origin GET requests to /api/tasks/<id>. Otherwise return the string direct. Do not fetch any URL in this function.

Input fieldMeaning

Return value: A Boolean. Return true only for the exact matching source/origin/current generation and the fragment.ready/version 1 message schema. Return false for a mismatched condition.
