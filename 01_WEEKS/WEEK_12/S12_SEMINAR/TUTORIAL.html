S12 — Recipient identity, job transitions and reply correlation

What you will do and why

Asynchronous work can finish after a newer action or be delivered more than once. Before using a real queue or socket, you will model three safeguards: a collision-free recipient label, monotonic lifecycle state and settlement of the exact pending request.

Before you start: Read arrays and nested objects, create a copied state, understand string construction and distinguish an event from current state. Use S11’s identity/ownership idea when reasoning about recipient labels.

Observable learning outcomes

  1. Construct a recipient label containing both principal and connection identity without delimiter collisions.
  2. Preserve terminal job state and refuse decreasing progress.
  3. Accept only a correctly correlated reply while preserving other pending entries.

S11–S13 use bounded JavaScript models. They do not run Express, a queue framework, WebSocket delivery, a native Worker, a Service Worker or a cross-origin frame boundary. A classroom PASS concerns the supplied finite contract and input immutability. It does not complete the retained full application, authenticate authorship or qualify another OS/browser.

The full required v3.0.0 route is planned for 120–165 minutes. The workload remains unpiloted; all 3 projects are required individual work. Read the full-work allocation before class.

P01 — HTTP/WebSocket: recipient ownership

Two people can use the same connection label without being the same recipient. Encode both labels as a JSON tuple, so neither a shared label nor a delimiter inside a label collapses distinct identities. This does not establish that either label is authentic.

Editable target: CLASSROOM_RC6/student/p01.mjs
Exported function: recipientKey(input)

Read the input and output contract

Input fieldMeaning
principalIdNonblank string identifying the already selected principal.
connectionIdNonblank string identifying this principal’s connection.

Return value: The string produced by a JSON array containing the principal ID followed by the connection ID, or null for invalid/non-string/blank labels. Output is a string such as ["a","desk"], not a JavaScript array.

P02 — Queue: terminal state does not regress

Treat an event as a proposed change to a job, not as unquestionable replacement state. A job can advance from queued to active to completed/failed; its progress must not go backwards and terminal states must not reopen.

Exported function: jobTransition(input)

Read the input and output contract

Input fieldMeaning

Return value: A state-shaped object {status, progress} representing the allowed transition, or the preserved state values for terminal, decreasing or out-of-order events. Active progress belongs within 0–100; completion has progress 100. Do not mutate the input state.

P03 — Dispatcher: correlation and single settlement

A reply belongs to one pending request only when its request ID and expected completion type match. Settling it removes that entry once and leaves other work pending. Unknown IDs and wrong-type replies do not settle anything.

Editable target: CLASSROOM_RC6/student/p03.mjs
Exported function: settleOwned(input)

Read the input and output contract

Input fieldMeaning
pendingArray of {id, type} entries, where type is the requested operation label such as calculate.
replyObject with requestId, completion type and result.

Return value: An object {pending, settled}. For a matched reply, pending omits exactly that entry and settled is {id, result}. Otherwise pending preserves the entries and settled is null. Leave the supplied array and reply unchanged.
