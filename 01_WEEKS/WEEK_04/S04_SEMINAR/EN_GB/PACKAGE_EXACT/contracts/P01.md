# P01 — Multi-source Data Dashboard

**Required in-class core.** Edit only `projects/p01/public/dashboard.js`. The protected subtree is an exact canonical student copy. This complete public contract is a British English teaching derivation from canonical U03 P01 spec.md; it does not replace that source's identity.

## What is supplied and what is yours

HTML/CSS, the static server, three JSON fixtures, the renderer, bootstrap and canonical tests are supplied. Implement `loadDashboard({ fetchImpl = fetch, render })`. The controller receives a request function and a rendering callback; it does not reach into the DOM. No dependency installation is needed.

## Required behaviour

Call `render` immediately with `{ state: 'loading' }`. Initiate one request for each of `/data/profile.json`, `/data/tasks.json` and `/data/notices.json` before awaiting any individual result. Use `Promise.all` to combine independent work. Completion order need not match the path order; the aggregate positions must match the source identities.

For a response whose `ok` is false, raise the error message `request failed: <path> (<status>)`, with the actual path and status substituted. Do not treat a fulfilled 404 response as successful data. Parse successful response bodies. A transport rejection, rejected HTTP status or parsing failure must become the final `{ state: 'error', message }` model rather than leaving loading indefinitely or escaping as an unhandled rejection.

On success, create and render a model with exactly these assessed fields:

```text
state: "success"
profile: the profile value
openTaskCount: the number of tasks whose status is "open"
totalTaskCount: the tasks array length
notices: the notices value
```

Return the final model that was rendered. Preserve the supplied input values. Fetch each documented path once. The empty task array is a success with zero counts, not a new mandatory state. Retry, refresh racing, caching and arbitrary-data validation are not additions to this assessed contract.

## Which fixture are you observing?

Read `projects/p01/public/data/` before executing. The browser fixture contains a profile, three task records and two notices. The canonical objective test has a smaller, independent fixture. A count from one fixture cannot be presented as an observation of the other. Preserve your own predicted values in the form before inspecting output.
