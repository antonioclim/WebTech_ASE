# P02 — Interactive Task List

**Required portfolio after the seminar.** Source workload: 45–60 minutes, not a guaranteed duration or hidden extension of the core hour. Edit only `projects/p02/public/task-view.js`.

## Supplied boundary

The immutable task model, HTML/CSS, bootstrap, static server and tests are complete. Implement `renderTasks(tasks, { document, list })` and `bindTaskEvents({ form, list, onAdd, onToggle, onDelete })`. These are the only two missing exports. Rendering describes the current model; callbacks request changes through the supplied orchestration.

## Rendering contract

Clear the old list on every render. For each task create an `li` carrying `data-task-id`. Each row has a checkbox reflecting `completed`, a title element populated through `textContent` and a delete button carrying `data-action="delete"`. Completed rows have class `completed`. With no tasks, render one noninteractive empty-message row. Do not mutate task records or parse their titles as markup. Do not add row-level event listeners while rendering.

## Event and cleanup contract

The form submit handler prevents the default submission. Read the named `title` field, trim its text and call `onAdd(title)` only for a nonempty value. Reset after a valid add, not after a blank submission.

One delegated click listener on the list sends checkbox actions to `onToggle(id)` and delete-button or descendant actions to `onDelete(id)`. Resolve the containing row for the identifier. The element on which the listener is registered is not automatically the clicked row. Return `unbind()` and remove both your form and list listeners when it is called.

Use DOM creation and `textContent`; do not use `innerHTML`, row-level listeners, a framework or a new dependency. The supplied model remains the owner of task data. Storage, persistence, APIs, drag-and-drop and extra styling are outside the assessed task.
