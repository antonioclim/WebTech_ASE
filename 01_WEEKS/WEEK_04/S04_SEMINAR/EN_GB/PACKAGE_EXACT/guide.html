S04 — work from a prediction to a justified conclusion

The central question is not whether a dashboard appears eventually. It is whether your controller starts independent work at the right boundary, reaches the required state and returns a result that your evidence supports. Work individually and record the prediction before the run, including a wrong prediction when it teaches you something.

Before the meeting

Prepare the existing Day 0 runtime and read the launch guide. No installation is hidden inside the 60-minute seminar. Read the P01 public contract and the three supplied JSON files. Open the evidence form and enter the observed environment. UNKNOWN is honest; copying a reference version as a measured one is not.

E1: preserve the population you actually counted

Predict the profile, open/total task counts and notices from the supplied browser files. A canonical objective test uses a smaller fixture. Name the fixture in every count. Run your implementation, compare the actual final model and explain a disagreement without overwriting the original prediction.

E2: distinguish initiation from completion

The deferred observer records which request functions were called before releasing its controlled responses. It then releases work in a deliberately different order. Use its request list, release/completion list and rendered models to explain what the controller establishes. This is injected evidence, not a Network timing trace. It does not show that work runs on three processor threads or that failure cancels the other requests.

E3: locate one failure boundary

Predict the result before running transport, HTTP or parse scenarios. A request rejection has no successful response object. An HTTP error has a response that your policy must classify. Parsing can fail after a successful status. Record the actual error model and the exact action that produced it. The server's missing-tasks and malformed-tasks options change responses without modifying protected files.

E4: reconcile browser and controller evidence

Use the printed loopback URL and inspect actual requests, DOM state and console. Do not label a Node fake as a browser run. On a fast local response, loading may be too brief to see unaided; the documented delay is a labelled teaching intervention. A screenshot is useful only with its URL, action, scenario and interpretation. Never present a fixed expected trace as an observation of your edited file.

E5: one bounded Gemini review

Use GEMINI_PROMPT.txt with a sanitised claim, not an entire repository. Record the relevant prompt, the single claim and an independent check. ACCEPTED, REJECTED, PARTIALLY ACCEPTED and UNKNOWN are all legitimate evidence-based verdicts. Agreement with an AI response is not the objective. SYNTHETIC_OFFLINE_CLAIM.txt is practice only and must never be attributed to a real Gemini conversation.

What the test labels establish

Initial checks identify the known starter gap; complete checks assess the named bounded behaviour. A parse error, timeout, runtime guard or missing command is not an expected objective assertion. P02/P03 raw starter exceptions remain separate from the derived assertion-first route. The canonical fixtures and extra checks overlap; multiple executions do not create independent new coverage.

The minute-60 stop

Save a JSON draft. A student with an incomplete implementation records the real current failure and a next check. Required P02, delayed browser evidence or unavailable Gemini remain explicit. The final PDF is submitted after the separate portfolio window, not automatically at minute 60. A complete report of an unsuccessful implementation can be assessed honestly; it is not a passing grade merely because all form fields are filled.
