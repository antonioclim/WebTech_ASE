What you will learn

  • Use a single parameterised join and return detached relationship rows.
  • Pass one managed transaction through five awaited database operations.
  • Separate resource identity and repeated-method effects from changing response status.

P02 — One owned atomic booking

Edit only: CLASSROOM_RC6/targets/p02.mjs. Interface: await bookSeats(store, {eventId, attendeeId, seats, afterCreated}).

Reason about the boundary

The booking, available seats and audit form one atomic decision. An apparently correct booking row is insufficient if a later callback or audit failure leaves seats deducted. The same transaction object must cross every database operation.

Contract examples to predict before execution; these are not your observations
Input or conditionExpected contract behaviour
Available 5, requested 2; successful bookingAvailable 3, one booking, one audit
Callback or audit throws after creationDatabase snapshot returns to its before state; error is preserved
Duplicate attendee/event bookingbooking_exists before writes
Five database operation namesevent, duplicate, seats, create, audit

Implement in stages

1. Validate before database activity

Input, prediction and action. Read the existing positive-integer seats guard. Preserve it before managed is entered. Predict TypeError invalid_seats for 0.5, 0, -1, "2", NaN and Infinity, with no database operation or managed entry. Change only the relevant TODO area; the existing missing-event and sold-out decisions remain.

Why the change matters. A cheap decision based solely on input needs no transaction. Starting database work first makes the rejected quantity acquire an unnecessary state boundary. Numeric conversion would admit a different value from the one supplied. Event availability cannot be decided here because it is stored state.

3. Share and await the owned modification

Input, prediction and action. Plan the five database participants: event, duplicate, seats, create and audit. Use the same actual tx for each. Between create and audit await afterCreated({booking,transaction:tx}); it is a checkpoint, not a sixth database operation. Derive a fresh returned booking/available representation and return the managed operation’s result. Predict success 5→3 seats with one booking and one audit.

Why the change matters. Awaiting independent writes orders them but cannot reverse prior writes. The supplied managed adapter executes actual BEGIN and waits for the callback promise before COMMIT or ROLLBACK. An async return adopts a returned promise; the defect is abandoning work outside the callback’s settlement chain. A result constructed inside the callback is not yet an outer confirmed result.

These reads are on the owning connection, not proof of another reader’s isolation.

Save the full state before each fresh fixture. Let the supplied adapter handle rejection; do not swallow errors to manufacture success or add a retry policy.

Why the change matters. Both failures must cancel the database group, but they occur at different positions. A callback error identity should survive a successful rollback. The audit count alone cannot show that seats and booking were restored. Logging or a JavaScript array outside SQLite can survive rollback, as neutral demonstration 03 shows in a different domain.
