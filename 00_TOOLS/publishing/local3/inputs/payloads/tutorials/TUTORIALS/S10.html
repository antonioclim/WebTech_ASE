The small JavaScript interface you will edit

Each .mjs file exports a named function receiving one JavaScript object. JSON uses double-quoted property names and cannot contain comments. Arrays use square brackets and objects use braces. Read each nested property from the actual input. A returned boolean is true or false, not a quoted string. A returned error object is a result required by the contract, not necessarily a thrown exception. Keep the exported function name and its parameter. Replace the intentional TODO body with your own reasoning and code, then save with Ctrl+S or Cmd+S.

An immutable update means that the supplied input remains unchanged after your function returns. Compute a new result from it. Array operations such as filter produce an array; push changes the array it receives. Copying an outer object does not automatically copy a nested array. P01 · Implement explicit, immutable workshop state transitions

Several controls can update shared workshop state. A reducer-style function receives a state and an action, then returns the next state without modifying the old one. An explicit action contract prevents an unknown operation from silently changing data or being mistaken for successful work.

Read the interface before editing

workshopTransition(input) receives state and action. State contains track and savedIds, and may have unrelated properties to preserve. track/selected changes the track using action.track; session/toggled adds an absent action.id or removes a saved ID; saved/cleared empties saved IDs. Unsupported action types return {"error":"unsupported_action"} in this classroom API. The original state and arrays remain unchanged.

Editable file: CLASSROOM_RC6/student/p01.mjs. Named export: workshopTransition. The supplied fixtures live in CLASSROOM_RC6/support/cases.json and assertions in CLASSROOM_RC6/tests/objective.test.mjs.

Supplied contract fixtures: predictions to understand before implementation
CaseInputExpected output
1{"state":{"track":"all","savedIds":[]},"action":{"type":"track/selected","track":"web"}}{"track":"web","savedIds":[]}
2{"state":{"track":"all","savedIds":["a"]},"action":{"type":"session/toggled","id":"a"}}{"track":"all","savedIds":[]}
3{"state":{"track":"web","savedIds":["a"]},"action":{"type":"saved/cleared"}}{"track":"web","savedIds":[]}
4{"state":{"track":"all","savedIds":[]},"action":{"type":"unknown"}}{"error":"unsupported_action"}

The supplied cases select a different track, toggle an already saved ID off, clear saved IDs while preserving a web track and report an unknown action. A toggle is not unconditional addition, and clearing saved IDs is not resetting the whole state. The full developer-facing project has a different exception contract; use this classroom API rather than copying that expectation.

Implement and inspect in small steps

  1. Open CLASSROOM_RC6/student/p01.mjs. Keep workshopTransition. Write an action table with one row per supported action, the property that can change and the properties that must be retained.
  2. Make two predictions for toggle: when the ID is already saved and when it is absent. Decide how you will avoid mutating state.savedIds.
  3. Implement your own action dispatch and immutable updates. Preserve unrelated state in supported transitions. Keep the explicit unsupported_action output for an unrecognised type rather than throwing the historical full-project exception.
  4. Save and run the work command. If a clear/select operation drops another field, inspect how you reconstructed the state. If immutability fails, inspect assignments and mutating array operations.
  5. Run a distinct unsupported-action case and add your own valid transition with an unrelated synthetic state property to test preservation. Explain why each challenges a different possible fault.
Hint 1 · clarify the decision

The action type selects one operation. A saved ID is either present or absent before a toggle, so those branches need different next arrays.

Hint 2 · investigate a likely implementation mistake

Retain unrelated fields from the previous state while changing only the authorised one. Copying state but reusing and then mutating savedIds still changes the original nested array.

P02 · Accept the latest successful notification refresh and derive unread count

A notifications list needs two protections: stale replies must not overwrite data belonging to a newer owner, and failed refreshes must not erase previously known notifications. The unread count should then be calculated from whichever list is actually authoritative, rather than trusting a separate count that can drift.

Read the interface before editing

notificationRefresh(input) receives owner, reply, boolean success, current items and received. Items have id and read. It returns an object with items and unread. A matching successful refresh selects the whole received list. A stale reply or unsuccessful refresh retains current items. Derive unread from the selected list and preserve the input.

Editable file: CLASSROOM_RC6/student/p02.mjs. Named export: notificationRefresh. The supplied fixtures live in CLASSROOM_RC6/support/cases.json and assertions in CLASSROOM_RC6/tests/objective.test.mjs.

Supplied contract fixtures: predictions to understand before implementation
CaseInputExpected output
1{"owner":"B","reply":"A","success":true,"items":[{"id":"a","read":false}],"received":[]}{"items":[{"id":"a","read":false}],"unread":1}
2{"owner":"B","reply":"B","success":true,"items":[],"received":[{"id":"b","read":true}]}{"items":[{"id":"b","read":true}],"unread":0}
3{"owner":"B","reply":"B","success":false,"items":[{"id":"a","read":false}],"received":[]}{"items":[{"id":"a","read":false}],"unread":1}

Case 1 is successful but stale, so its empty received list cannot erase the old unread item. Case 2 matches ownership and succeeds, so the received read item becomes authoritative and unread is zero. Case 3 matches ownership but fails, so the old unread item remains. Matching identity and success are independent necessary conditions.

Implement and inspect in small steps

  1. Open CLASSROOM_RC6/student/p02.mjs. Keep notificationRefresh. Label the owner/reply fields and the two lists; note that this API explicitly includes success, unlike the earlier S09 refresh model.
  2. Before coding, decide which list is selected in every supplied fixture. Only after choosing that list calculate its unread count.
  3. Implement your own selection and derived count. Do not merge old and received lists, mark items read as a side effect or accept a stale successful reply. Return the required object shape rather than only a number.
  4. Save and run the work command. If the list is correct but unread is wrong, check which array was counted and what the read flags mean.
  5. Run your own matching but failed refresh with very different received data. Optionally compare with the identical fixture where only success changes; separate the two observations and preserve both predictions.
Hint 1 · clarify the decision

An old item with read false contributes to unread; a read true item does not. Count the chosen list, not always items or always received.

Hint 2 · investigate a likely implementation mistake

Choose authority before deriving secondary values. A failure is not an authoritative empty response, even when received happens to be empty.

P03 · Filter for required capabilities before comparing declared costs

Choosing a low-cost design that cannot perform a required task is not a useful optimisation. This exercise separates eligibility from ranking. It also refuses to pretend a tied ranking contains one unambiguous winner. Costs are supplied exercise values, not performance measurements or universal claims about real libraries.

Read the interface before editing

chooseArchitecture(input) receives required (an array of capability labels) and candidates. Each candidate has id, capabilities and a declared nonnegative cost. Exclude any candidate lacking any required capability. Return the sole lowest-cost eligible candidate ID, or null when none is eligible or the minimum is tied. Preserve input arrays and objects.

Editable file: CLASSROOM_RC6/student/p03.mjs. Named export: chooseArchitecture. The supplied fixtures live in CLASSROOM_RC6/support/cases.json and assertions in CLASSROOM_RC6/tests/objective.test.mjs.

Supplied contract fixtures: predictions to understand before implementation
CaseInputExpected output
1{"required":["shared"],"candidates":[{"id":"lifted","capabilities":[],"cost":1},{"id":"context","capabilities":["shared"],"cost":3}]}"context"
2{"required":[],"candidates":[{"id":"a","capabilities":[],"cost":2},{"id":"b","capabilities":[],"cost":2}]}null
3{"required":["async"],"candidates":[{"id":"a","capabilities":[],"cost":1}]}null

In the first supplied fixture the cheap lifted candidate lacks shared capability, so context wins despite higher cost. The second fixture has no required capability but two equal-cost eligible candidates, so there is no sole winner. The third requires async and has no eligible candidate. Returning the first array item would silently conceal two distinct no-winner cases.

Implement and inspect in small steps

  1. Open CLASSROOM_RC6/student/p03.mjs. Keep chooseArchitecture. On paper mark whether each candidate has every required capability before looking at its cost.
  2. For the eligible set identify the minimum declared cost and the number of candidates sharing that minimum. A tie at a higher cost does not itself prevent a unique lower-cost winner.
  3. Implement your own eligibility and ranking decisions. Avoid sorting the supplied candidate array in place; that would alter input order. Do not invent a default winner when the eligible set is empty or the minimum is tied.
  4. Save and run the work command. Confirm the result is an ID string or null, not an entire candidate object, a cost number or the string “null”.
  5. Run a distinct synthetic tie or no-eligible case. To isolate capability filtering, include a cheaper ineligible candidate and explain why its cost cannot override missing capability.
Hint 1 · clarify the decision

Eligibility is an all-required-capabilities condition, not a match of at least one label. An empty required list makes every otherwise valid candidate eligible in this exercise.

Hint 2 · investigate a likely implementation mistake

Find the minimum among eligible candidates, then establish uniqueness at that minimum. The order in which tied candidates were supplied is not a stated tie-break rule.
