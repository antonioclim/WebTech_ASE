The small JavaScript interface you will edit

Each .mjs file exports a named function receiving one JavaScript object. JSON uses double-quoted property names and cannot contain comments. Arrays use square brackets and objects use braces. Read each nested property from the actual input. A returned boolean is true or false, not a quoted string. A returned error object is a result required by the contract, not necessarily a thrown exception. Keep the exported function name and its parameter. An immutable update means that the supplied input remains unchanged after your function returns. Compute a new result from it. P01 · Add a reading item while preserving existing state

A user submits a title to a reading queue. An empty submission should not create a meaningless item, and a valid submission should not alter the previously supplied queue. A stable opaque ID is provided by the caller: the state transition must not invent a second ID or use the title as identity.

Read the interface before editing

queueAdd(input) receives items (an array of reading-item objects), title (a string) and id (the opaque ID for a new item). It returns the resulting item array. A newly added item has the supplied ID, the trimmed title and read: false. For whitespace-only input the existing queue content is retained. For a valid addition the result must be a new array and the original input must remain unchanged.

Editable file: CLASSROOM_RC6/student/p01.mjs. Named export: queueAdd. The supplied fixtures live in CLASSROOM_RC6/support/cases.json and assertions in CLASSROOM_RC6/tests/objective.test.mjs.

In supplied case 1, trimming removes surrounding spaces from “Book”; it does not change internal spaces. P02 · Derive capacity without a second mutable state

A workshop dashboard shows how many seats are used and how many remain. If “used”, “remaining” and the attendee list are all separately stored and changed, they can disagree. This function derives one view from the supplied attendee array and capacity instead.

Read the interface before editing

capacityView(input) receives capacity and attendees. For valid capacity it returns exactly an object with used, remaining and full. Negative capacity, non-integer capacity or an attendee count above capacity returns {"error":"invalid_capacity"}. The input stays unchanged.

Editable file: CLASSROOM_RC6/student/p02.mjs. Named export: capacityView. The supplied fixtures live in CLASSROOM_RC6/support/cases.json and assertions in CLASSROOM_RC6/tests/objective.test.mjs.

Supplied contract fixtures: predictions to understand before implementation
CaseInputExpected output
1{"capacity":5,"attendees":["a","b"]}{"used":2,"remaining":3,"full":false}
2{"capacity":2,"attendees":["a","b"]}{"used":2,"remaining":0,"full":true}
3{"capacity":1,"attendees":["a","b"]}{"error":"invalid_capacity"}

Case 1 has two attendees and capacity five: used is two, remaining is three and full is false. Case 2 reaches capacity exactly and returns full true. Case 3 is already over capacity, so clamping remaining to zero would hide invalid input; the explicit error object is required.

  3. Write the rejection branch in your own code. For the valid branch calculate the three related outputs from the same capacity and attendee count. Do not change or remove attendees to make invalid data fit.
  4. Save and run the work command. If the full flag fails at the equality boundary, compare “exactly full” with “already over capacity” rather than treating both as the same valid state.
  5. Create and run your own additional negative or equality-boundary fixture. Record the expected error/result before the run and compare the actual_output yourself.
Hint 1 · clarify the decision

A count is the array length, not the text of the last attendee or the number of unique names. The contract uses the supplied attendee array as the source of truth.

Hint 2 · investigate a likely implementation mistake

Separate validation from projection. Once valid, used plus remaining must equal capacity. Only a valid view can claim a full workshop; an invalid-capacity error is not that view.

P03 · Decide which reply still has permission to publish

Two searches can finish in a different order from the order they started. Request B may become current before the slower request A finishes. A late reply should update the interface only if it still owns the current request and the lifecycle remains active. Cancellation is related, but it is not itself the publication decision.

Read the interface before editing

mayPublish(input) receives boolean active, opaque currentId and opaque requestId. It returns a boolean permission. A matching request ID is insufficient when the lifecycle is inactive; an active lifecycle is insufficient for a stale request ID. It changes no input.

Editable file: CLASSROOM_RC6/student/p03.mjs. Named export: mayPublish. The supplied fixtures live in CLASSROOM_RC6/support/cases.json and assertions in CLASSROOM_RC6/tests/objective.test.mjs.

Supplied contract fixtures: predictions to understand before implementation
CaseInputExpected output
1{"active":true,"currentId":"B","requestId":"B"}true
2{"active":true,"currentId":"B","requestId":"A"}false
3{"active":false,"currentId":"A","requestId":"A"}false

Read the supplied cases as an event-order thought experiment: B is current and B replies, then B is still current and A replies, then the owner is inactive even though IDs match. The outputs are true, false and false. This predicts permission, not whether a real fetch was aborted.

Implement and inspect in small steps

  1. Open CLASSROOM_RC6/student/p03.mjs. Keep mayPublish. Label the current owner and arriving reply in each fixture; do not infer that alphabetical order determines freshness.
  2. Make a two-condition truth table on paper: active/inactive and matching/different IDs. Write one prediction for every combination. Only one combination permits publication.
  3. Implement your own boolean predicate from those two independent requirements. Do not introduce timers, fetch or an AbortController into this small interface.
  4. Save and run the work command. Check that the output is a boolean, not a string or an object. If stale replies pass, inspect the ID comparison; if inactive ownership passes, inspect the lifecycle condition.
  5. Run a distinct inactive or stale synthetic case. Explain why a successful network response would still not be permitted to publish in that case.
Hint 1 · clarify the decision

Opaque IDs are compared for ownership. Their values do not tell you how many milliseconds elapsed or whether cancellation succeeded.

Hint 2 · investigate a likely implementation mistake

Reason about two necessary conditions together. Returning permission from only one condition will admit either an inactive owner or an old reply.
