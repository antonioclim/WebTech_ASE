## Implemented installation scope

Linux automation targets Ubuntu 22.04, 24.04 and 26.04 plus Debian 12 and 13 on x64 or ARM64 with the declared local desktop, systemd and glibc conditions. Fedora and other unqualified distributions receive inspection or audit, not guessed APT commands.

macOS automation targets native Apple Silicon on major releases 15, 26 and 27 plus Intel on 15 and 26. These are explicit implementation gates, not a vendor support guarantee for every model. A Mac using Rosetta is subject to native-process selection. An unlisted platform does not become supported because the latest package has a newer filename.

## What can count as target evidence later

Use the relevant README route under the intended normal account. A completed audit must carry matching readiness, maintenance and completion information. If accounts are declared, preserve their classification as local acknowledgements. Keep the generated evidence archive and inspect it before sharing. A test of one machine does not certify every OS/architecture combination.

For desktop use, the visible editor and course terminal must actually open as expected. The exact runtime pair must be verified in the selected course context. Browser access, developer tools and online account access need personal observation when those activities are required. A package detected in metadata is not a GUI acceptance test.

Do not close these conditions by disabling Gatekeeper, an Electron sandbox, corporate policies or package-manager locks. Do not use fabricated acknowledgements to force a ready verdict. No password, code, token or live credential is needed to continue ordinary local support.

No extra production phase is required merely to retain these honest evidence limits. A specific failure on a target remains a troubleshooting incident, not a retrospective claim that it was already tested.
